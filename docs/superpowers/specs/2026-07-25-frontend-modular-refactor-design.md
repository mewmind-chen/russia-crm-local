## 1. 背景

TradePulse 已经具备完整的外贸客户开发、CRM、AI 工作站、治理、通知、权限和发布能力，
但正式前端仍以一个约 3700 行的 `sales-assets/app.js` 和静态 `sales-crm.html` 为中心。
页面渲染、状态、路由、权限、轮询、弹窗和业务动作集中在同一闭包中，新增功能会继续扩大
耦合和回归范围。

`ux-preview` 已验证角色首页、精简导航、统一客户详情、模块搭建和 8 个 AI 工作站的目标
信息架构，但它是硬编码的纯前端内存原型，不能替代正式仓库中的真实数据、权限、审计、
AI Control Plane、发布和回滚能力。

本重构以 `russia-crm-local` 为唯一正式产品，把 `ux-preview` 作为交互合同，使用原生
JavaScript 在现有 Express + SQLite 系统内渐进迁移。重构完成后停止维护独立原型。

## 2. 已确认的全局硬约束

### 2.1 零功能遗漏

重构只改变功能的组织方式、代码边界和呈现位置，不删除、降级或替换现有能力。

实施基线取以下集合的并集，而不是只取原型中可见的功能：

1. 实施启动时最新 `origin/main` 中所有非退役功能。
2. 当时生产环境已发布并启用的全部功能。
3. 所有仍受支持的页面、深链、API、权限、feature flag、后台 Worker、报表和维护入口。
4. 已合并但尚未完成生产发布的功能，避免重构分支重新引入旧代码。

每项能力必须进入“旧入口 → 新模块 → 权限 → feature flag → API → 测试 → 发布状态”
迁移矩阵。矩阵存在未映射或未验收条目时，不允许宣布重构完成。

### 2.2 默认保留全部能力

- 导航合并等于移动入口，不等于删除功能。
- 无权限功能继续不渲染；有权限且已启用的功能默认可见。
- 不新增业务功能的默认关闭项。
- 后续是否关闭某项业务能力，由产品负责人单独通过现有权限或 feature flag 决定。
- 临时重构发布开关只用于新旧外壳切换，不得改变业务能力本身；完成切换后删除。

### 2.3 技术边界

- 保留 Node.js、Express、SQLite、原生 HTML/CSS/JavaScript。
- 不引入 React、Vue、前端构建工具或第二套业务数据模型。
- 不重写现有服务端权限、幂等、审计、AI 路由和业务规则。
- 继续使用现有 `/api/sales-crm/*`、AI、Recon、报告和会话接口。
- 新前端模块必须尊重服务端返回的权限和行级范围，不能把前端隐藏当作安全边界。
- 所有关键写入继续由服务端作最终校验。

## 4. 目标信息架构

### 4.1 销售

一级入口保持为 4 个：

1. **我的今日**：待我领取、我的预警、今天该跟进、AI 待复核。
2. **我的客户**：客户列表、当前阶段管道、筛选导出、AI 资料包入口。
3. **我的线索**：全部、待审核、待分配、待领取、已领取、已退回。
4. **AI 助手**：全局唯一助手入口，客户上下文随详情切换。

销售已有但不适合作为一级导航的功能，迁入上述页面或客户详情，功能本身保留。

### 4.2 经理

一级入口保持为 6 个：

1. **经营驾驶舱**：团队指标、累计漏斗、需要处理、动作 feed。
2. **今日待办**：规则异常、AI 解释和经理介入。
3. **线索分配**：审核、分配、AI 优先级、销售匹配和人工裁决。
4. **团队客户**：客户列表和当前阶段管道。
5. **团队洞察**：销售能力、经理评价、市场策略、销售辅导。
6. **情报中心**：线索池、负责人线索和 Recon 情报。

AI 助手继续作为全局入口，不重复成为业务页面。

### 4.3 管理员

管理员拥有经理的完整能力，并增加“系统管理”分组：

- 用户与权限
- AI 任务与版本治理
- 客户回收站
- 数据维护
- AI 引擎和业务 feature flags

### 4.4 路由兼容

- 新路由使用稳定 hash，并由注册表统一管理。
- 旧 `#pending`、`#claimed`、`#pipeline`、`#team`、`#insights`、`#markets`、
  `#pool`、`#contacts`、`#recon` 和 `#customerProfile` 保留兼容映射。
- 旧客户深链中的 `?customer=<id>#customerProfile` 必须重定向到新客户详情且保留客户 ID。
- 浏览器前进、后退、刷新和直接输入深链必须得到同一页面状态。
- 无权限深链显示明确的无权限状态，然后回到该角色首页；URL 与实际视图必须一致。


`app.js` 最终只负责启动、装配依赖、加载会话和启动路由。业务渲染不再回流到 `app.js`。

### 5.2 模块合同

每个页面模块实现同一合同：

```js
{
  id: 'my-today',
  routes: ['my-today'],
  roles: ['sales'],
  permissions: ['view_customers', 'view_intake'],
  featureFlags: [],
  async load(context) {},
  render(context) {},
  dispose(context) {},
}
```

- `load` 只加载该模块所需数据。
- `render` 只更新自己的挂载点。
- `dispose` 必须取消轮询、未完成请求、订阅和临时事件监听。
- 模块不能直接访问其他模块内部状态。
- 跨模块动作通过 service 和 store invalidation 协作。

### 5.3 页面与模块注册

`core/registry.js` 是页面、权限、角色、feature flag、旧路由别名和默认首页的唯一来源。
导航从注册表生成，不再在 HTML 中硬编码一套、JavaScript 中再维护一套。

权限和 feature flag 的处理顺序为：

```text
服务端 capabilities
  -> 角色和权限判断
  -> feature flag 判断
  -> 用户布局偏好
  -> 最终可见模块
```

无权限或 flag 关闭的模块不进入 DOM，也不能通过保存的布局偏好恢复。

### 5.4 状态与数据流

全局 store 只保留：

- 当前用户、权限和身份检查状态
- feature flags 和 AI 引擎摘要
- 当前路由及客户上下文
- 导航计数和共享字典
- 各领域的独立数据分区

启动时的 bootstrap 只负责全局信息。线索、情报、AI 任务、治理和客户详情改为按页面加载。

标准写入流程：

```text
用户操作
  -> service 调用现有 API
  -> 服务端权限、规则、幂等和审计
  -> 返回权威结果
  -> 更新对应 store 分区
  -> invalidation 导航计数和关联模块
  -> 局部重渲染
```

关键写入不做乐观更新。领取、批量分配、报价、订单、AI 建议采纳、维护和治理操作只有在
服务端成功后才更新界面。

## 8. 错误处理

| 状态 | 前端行为 |
|---|---|
| 401 | 清理会话相关状态并返回登录页 |
| 403 | 不渲染入口；深链显示无权限状态并回角色首页 |
| 404 | 显示对象不存在或已不可见，不保留失效详情 |
| 409 / stale | 告知数据已变化，刷新权威数据后要求用户重新确认 |
| 422 | 在具体字段或操作区显示服务端校验信息 |
| 网络 / 5xx | 保留已加载数据，模块内显示重试，不清空整个工作区 |
| AI 失败 | 展示规则回退和人工路径，不阻断 CRM |

错误消息继续使用服务端脱敏摘要，不展示 Prompt、密钥、完整任务输入、租约或 Worker 内部字段。

## 9. 响应式与可访问性

### 9.1 响应式

- 桌面继续使用侧栏和高密度工作区。
- 780px 以下不保留窄侧栏 + 窄主栏结构。
- 销售移动端使用 4 个主入口；经理和管理员显示高频入口与“更多”菜单。
- 数据表使用稳定的横向滚动容器和边缘提示；关键动作保持可见。
- 客户详情在移动端改为全页，tab 可横向滚动，不使用覆盖大部分视口的窄抽屉。
- 弹窗内容区滚动、操作区吸底。
- 390px 验收要求 `documentElement.scrollWidth === clientWidth`，明确允许横向滚动的数据表除外。

### 9.2 可访问性

- 所有图标按钮和开关有可访问名称。
- modal 和 drawer 使用正确 dialog 语义、焦点进入、焦点恢复和 Esc 关闭。
- tab、segmented control、菜单和通知状态具备对应 ARIA 状态。
- 颜色不能作为风险、AI 或状态的唯一表达。
- 键盘可完成导航、筛选、打开详情、切换 tab 和关闭弹层。

## 10. 渐进迁移

### 阶段 0：功能资产与回归基线

- 固定启动 SHA、生产 SHA 和功能并集。
- 建立迁移追踪矩阵。
- 记录三角色导航、页面、深链、权限、API、Worker 和发布基线。
- 补齐缺失的契约测试后才开始拆分。

### 阶段 1：核心层抽取

- 抽出 API、状态、访问控制、路由和生命周期。
- 抽出 modal、drawer、table、empty-state 和 AI 结果组件。
- 保持现有页面、URL 和视觉不变。
- 完整回归通过后合并。

### 阶段 2：角色外壳与首页

- 注册表生成导航。
- 上线销售“我的今日”和角色默认首页。
- 合并重复导航入口，保留旧 hash 别名。
- 旧渲染器继续承载尚未迁移的页面。

### 阶段 3：核心经营工作流

- 迁移线索、客户列表、当前阶段管道、预警、通知和快速更新。
- 完成漏斗累计口径和列表当前口径。
- 所有预警在两步内到达处理动作。

### 阶段 4：统一客户详情

- 迁移完整资料、联系人、跟进、商务、Recon、评价、标签和 AI。
- 通过 iframe 退役门后删除 iframe。
- 保留旧深链兼容。

### 阶段 5：管理与 AI

- 迁移团队洞察、情报中心、用户权限、回收站和维护。

### 阶段 6：模块搭建与质量收口

- 上线角色默认布局和用户布局偏好。
- 权限和 feature flag 优先于偏好。
- 完成移动端、键盘和可访问性。
- 完成全功能等价审计。

### 阶段 7：切换与退役

- 临时发布开关切换到新外壳。

- 保留一个明确回滚 release。
- 稳定观察期通过后删除旧外壳和临时发布开关。
- 将 `ux-preview` 标记为只读历史参考并停止维护。

## 11. 临时发布开关

`CRM_UX_REDESIGN_ENABLED` 只控制新旧前端外壳，不控制任何业务功能。

- 关闭：使用旧导航和旧页面组合。
- 开启：使用新注册表、角色首页和模块组合。
- 两种外壳调用相同 service、API 和业务规则。
- 迁移期旧路由别名在两种外壳中都有效。
- 全量切换稳定后删除该开关，避免永久维护双外壳。

- 旧深链和新深链
- 前进、后退和刷新
- 搜索、分页、筛选、导出
- 客户详情全部 tab
- 关键写入和确认
- AI 开启、关闭、失败和 stale
- 无权限和身份检查
- 无控制台错误
- 无页面级横向溢出或控件遮挡

### 12.3 功能等价门

每个迁移矩阵条目必须同时具备：

1. 新入口或明确的归并位置。
2. 相同或更严格的角色、权限和行级范围。
3. 相同业务 API 或经批准的兼容 API。
4. 正常、空、错误和无权限状态。
5. 自动化测试证据。
6. 浏览器验收证据。
7. 旧入口的保留、别名或退役决定。

## 13. 回滚

- 每个阶段独立 PR、独立完整回归、独立生产发布。
- 数据库迁移与纯前端迁移分离；无必要不新增数据库迁移。
- 新外壳异常时关闭临时发布开关，回到同一 release 中的旧外壳。
- release 异常时使用现有 `previous` 完整回滚。
- 不自动恢复数据库；涉及数据库时继续遵循现有手工恢复边界。

## 14. 风险与控制

| 风险 | 控制 |
|---|---|
| 重构遗漏隐藏功能 | 功能并集、迁移矩阵、三角色遍历和旧路由清单 |
| `app.js` 拆分时行为变化 | 先抽取后改 UI，每个抽取阶段完整回归 |
| 新旧状态不同步 | 两种外壳共用 store、service 和 API，不复制业务状态 |
| 轮询和事件泄漏 | 统一 lifecycle 和强制 `dispose` |
| iframe 过早删除 | 独立 iframe 退役门 |
| 移动端再次退化 | 390px 每阶段验收，不留到最后一次修复 |
| AI 功能被导航收敛隐藏 | 每个工作站明确业务路标和任务中心入口 |
| 永久维护两套外壳 | 临时开关有明确删除阶段和完成条件 |

## 15. 完成定义

只有同时满足以下条件，前端重构才算完成：

1. 功能迁移矩阵无未映射、未测试或未决定条目。
2. 实施基线中的全部正式能力在新外壳中可达。
3. 三角色权限和客户范围无扩大、无泄露。
4. 旧深链有兼容行为。
5. 客户详情 iframe 已通过退役门并删除。
6. 8 个 AI 工作站、AI 补全、任务中心和治理能力完整可达。
7. AI 故障不阻断 CRM 人工流程。
8. 桌面和 390px 无页面级横向溢出、遮挡或不可操作控件。
9. 完整自动化回归、浏览器回归、生产 smoke、备份和回滚验证通过。
10. 临时发布开关和旧外壳已删除。
11. `ux-preview` 已停止作为并行产品维护。
