> 日期：2026-07-25
>
> 设计基线：`origin/main @ 79800f529d1d98e8a936959d88cbbbebce6f559f`
>
> 交互参考：`/Users/ylf/Documents/kimi/Workspaces/gi/ux-preview/index.html`

## 1. 背景

TradePulse 已经具备完整的外贸客户开发、CRM、AI 工作站、治理、通知、权限和发布能力，
但正式前端仍以一个约 3700 行的 `sales-assets/app.js` 和静态 `sales-crm.html` 为中心。
页面渲染、状态、路由、权限、轮询、弹窗和业务动作集中在同一闭包中，新增功能会继续扩大
耦合和回归范围。

`ux-preview` 已验证角色首页、精简导航、统一客户详情、模块搭建和 8 个 AI 能力的交互
参考，但它是硬编码的纯前端内存原型，不能替代正式仓库中的真实数据、权限、审计、
AI Control Plane、发布和回滚能力。

本重构以 `russia-crm-local` 为唯一正式产品，把 `ux-preview` 作为交互合同，使用原生
JavaScript 在现有 Express + SQLite 系统内渐进迁移。重构完成后停止维护独立原型。

## 2. 已确认的全局硬约束

### 2.1 零功能遗漏

重构只改变功能的组织方式、代码边界和呈现位置，不删除、降级或替换现有能力。

实施基线取以下集合的并集，而不是只取原型中可见的功能：

1. 实施启动时最新 `origin/main` 中所有非退役功能。
2. 当时生产环境已发布并启用的全部功能。
3. 所有仍受支持的页面、深链、API、权限、feature flag、后台 Worker、报表和维护入口。
4. 已合并但尚未完成生产发布的功能，避免重构分支重新引入旧代码。

每项能力必须进入“旧入口 → 新模块 → 权限 → feature flag → API → 测试 → 发布状态”
迁移矩阵。矩阵存在未映射或未验收条目时，不允许宣布重构完成。

### 2.2 默认保留全部能力

- 导航合并等于移动入口，不等于删除功能。
- 无权限功能继续不渲染；有权限且已启用的功能默认可见。
- 不新增业务功能的默认关闭项。
- 后续是否关闭某项业务能力，由产品负责人单独通过现有权限或 feature flag 决定。
- 临时重构发布开关只用于新旧外壳切换，不得改变业务能力本身；完成切换后删除。

### 2.3 技术边界

- 保留 Node.js、Express、SQLite、原生 HTML/CSS/JavaScript。
- 不引入 React、Vue、前端构建工具或第二套业务数据模型。
- 不重写现有服务端幂等、审计、AI 路由和业务规则。
- 权限默认保持等价；本设计唯一明确收紧是模型与版本治理从“管理员或经理”改为
  “仅管理员”。经理仍可按 `review_ai_tasks` 权限复核授权范围内的业务结果和运行故障。
- 继续使用现有 `/api/sales-crm/*`、AI、Recon、报告和会话接口。
- 新前端模块必须尊重服务端返回的权限和行级范围，不能把前端隐藏当作安全边界。
- 所有关键写入继续由服务端作最终校验。

## 4. 目标信息架构

### 4.1 销售

一级入口保持为 4 个：

1. **我的今日**：待我领取、我的预警、今天该跟进、AI 待复核。
2. **我的客户**：客户列表、当前阶段管道、筛选导出、AI 资料包入口。
3. **我的线索**：全部、待审核、待分配、待领取、已领取、已退回。
4. **AI 助手**：全局唯一助手入口，客户上下文随详情切换。

销售已有但不适合作为一级导航的功能，迁入上述页面或客户详情，功能本身保留。

### 4.2 经理

一级入口保持为 6 个：

1. **经营驾驶舱**：团队指标、累计漏斗、需要处理、动作 feed。
2. **今日待办**：规则异常、AI 解释和经理介入。
3. **线索分配**：审核、分配、AI 优先级、销售匹配和人工裁决。
4. **团队客户**：客户列表和当前阶段管道。
5. **团队洞察**：销售能力、经理评价、市场策略、销售辅导。
6. **情报中心**：线索池、负责人线索和 Recon 情报。

AI 助手继续作为全局入口，不重复成为业务页面。

### 4.3 管理员

管理员拥有经理的完整能力，并增加“系统管理”分组：

- 用户与权限
- AI 运行审计与版本治理
- 客户回收站
- 数据维护
- AI 引擎和业务 feature flags

### 4.4 路由兼容

- 新路由使用稳定 hash，并由注册表统一管理。
- 旧 `#pending`、`#claimed`、`#pipeline`、`#team`、`#insights`、`#markets`、
  `#pool`、`#contacts`、`#recon` 和 `#customerProfile` 保留兼容映射。
- 旧客户深链中的 `?customer=<id>#customerProfile` 必须重定向到新客户详情且保留客户 ID。
- 浏览器前进、后退、刷新和直接输入深链必须得到同一页面状态。
- 无权限深链显示明确的无权限状态，然后回到该角色首页；URL 与实际视图必须一致。


`app.js` 最终只负责启动、装配依赖、加载会话和启动路由。业务渲染不再回流到 `app.js`。

### 5.2 模块合同

每个页面模块实现同一合同：

```js
{
  id: 'my-today',
  routes: ['my-today'],
  roles: ['sales'],
  permissions: ['view_customers', 'view_intake'],
  featureFlags: [],
  async load(context) {},
  render(context) {},
  dispose(context) {},
}
```

- `load` 只加载该模块所需数据。
- `render` 只更新自己的挂载点。
- `dispose` 必须取消轮询、未完成请求、订阅和临时事件监听。
- 模块不能直接访问其他模块内部状态。
- 跨模块动作通过 service 和 store invalidation 协作。

### 5.3 页面与模块注册

`core/registry.js` 是页面、权限、角色、feature flag、旧路由别名和默认首页的唯一来源。
导航从注册表生成，不再在 HTML 中硬编码一套、JavaScript 中再维护一套。

权限和 feature flag 的处理顺序为：

```text
服务端 capabilities
  -> 角色和权限判断
  -> feature flag 判断
  -> 用户布局偏好
  -> 最终可见模块
```

无权限或 flag 关闭的模块不进入 DOM，也不能通过保存的布局偏好恢复。

### 5.4 状态与数据流

全局 store 只保留：

- 当前用户、权限和身份检查状态
- feature flags 和 AI 引擎摘要
- 当前路由及客户上下文
- 导航计数和共享字典
- 各领域的独立数据分区

启动时的 bootstrap 只负责全局信息。线索、情报、AI 任务、治理和客户详情改为按页面加载。

标准写入流程：

```text
用户操作
  -> service 调用现有 API
  -> 服务端权限、规则、幂等和审计
  -> 返回权威结果
  -> 更新对应 store 分区
  -> invalidation 导航计数和关联模块
  -> 局部重渲染
```

关键写入不做乐观更新。领取、批量分配、报价、订单、AI 建议采纳、维护和治理操作只有在
服务端成功后才更新界面。

## 7. AI 业务决策体验

### 7.1 现状核验与设计判断

2026-07-25 对生产库只读核验得到：

| 数据 | 数量 | 产品含义 |
|---|---:|---|
| 客户池 | 1902 | 真实业务数据 |
| Recon 证据 | 1959 | 带来源的研究事实，不等于每个客户都有完整证据 |
| 候选联系人 | 537 | 候选事实，仍可能需要就业关系和联系方式复核 |
| CRM 销售账户 | 15 | 当前实际销售经营样本很小 |
| 活动 / RFQ / 报价 / 订单 | 8 / 1 / 0 / 0 | 不足以支持稳定的团队经营或成交归因结论 |
| AI 任务 / 结构化结果 / 模型运行 | 18 / 15 / 22 | AI 确实运行过，但覆盖率低，不能表示全客户已分析 |

模型运行记录包含 DeepSeek、Kimi 和 Qwen 的真实调用、状态与费用。AI 输出是模型基于
允许证据做出的推断，不因调用了真实模型而自动成为事实。

现有 18 个 AI 任务中，只有 1 个同时记录了 `event_type` 和 `event_id`；3 个补全工作流
节点可追溯到同一个 workflow，但只有补全运行表拥有 `trigger_source`。`created_by` 只能
说明任务归属或发起人，不能替代“用户点击、业务事件、自动流程、定时任务或上线验收”等
触发原因。因此历史任务必须诚实显示“触发来源未记录”，不能由前端猜测。

### 7.2 产品主线

普通用户看到的不是“AI 工作站”，而是一条嵌入业务页面的决策链：

```text
来源事实 / 确定性规则
  -> AI 推断或解释
  -> 人工查看证据与限制
  -> 人工采纳、修改或拒绝
  -> 服务端执行明确的业务动作
  -> 审计记录结果
```

页面必须把这五层分开：

1. **来源事实**：CRM 记录、用户录入、带 URL 的 Recon 证据、确定性聚合指标。
2. **规则结果**：例如超期、资料缺失、样本门槛；规则不是 AI。
3. **AI 推断**：评分、摘要、解释、建议和草稿，统一标记“AI 推断”。
4. **人工决定**：采纳、修改后采纳、拒绝或暂不处理。
5. **系统动作**：只有人工确认后才允许写入 CRM、进入待办或触发受控流程。

“置信度”和“数据覆盖”是两个不同指标。高置信度不能掩盖证据少；覆盖充分也不能把
模型判断变成事实。

### 7.3 AI 结果合同

所有面向业务用户的 AI 结果复用 `ai-result` 组件，并按固定顺序回答：

| 区域 | 必须显示 |
|---|---|
| 这是什么 | 业务名称、`AI 推断` 标签、生成时间、是否过期 |
| 为什么出现 | 触发方式、触发业务事件、发起人或系统流程；缺失时明确写“来源未记录” |
| 根据什么 | 引用的事实摘要、证据数量、来源链接、更新时间和受限字段说明 |
| 结果是什么 | 结论、理由、置信度、覆盖状态、缺失信息和适用限制 |
| 可以做什么 | 查看依据、重新生成、采纳、修改后采纳、拒绝或关闭 |
| 动作会发生什么 | 确认前逐项说明将写入的字段、创建的记录、通知对象和不会发生的副作用 |

结果默认展示业务解释，模型、Prompt、token、费用、fallback 和 trace 放在管理员审计详情，
不与结论并列干扰销售判断。证据受权限和字段脱敏约束；无权查看的证据只显示“部分依据因
权限不可见”，不能泄露摘要。

### 7.4 触发来源合同

通用 AI 任务必须具备可审计的触发来源，不再只依赖工作站自定义字段：

```text
trigger_source:
  manual | business_event | workflow | schedule | api | migration | release_validation | legacy_unknown
trigger_event_type
trigger_event_id
trigger_actor_id
trigger_workflow_id
trigger_reason
triggered_at
```

- 新任务缺少 `trigger_source` 时服务端拒绝入队。
- `business_event` 必须同时提供事件类型和事件 ID。
- `workflow` 必须提供 workflow ID，并可追溯到最初发起方式和发起人。
- 自动触发显示具体规则，不使用笼统的“系统生成”。
- 历史数据统一回填 `legacy_unknown`；除非存在权威关联，不推测来源。
- 任务详情、业务结果和审计日志使用同一份来源信息。

实施时允许把现有 `event_type`、`event_id`、`created_by` 和 `workflow_id` 迁入该合同，
但不能改变原始值或伪造历史来源。

### 7.5 覆盖与样本充分性

所有 AI 入口先显示数据覆盖，再决定是否允许生成：

| 状态 | 含义 | 行为 |
|---|---|---|
| 无依据 | 没有可用事实或证据 | 不调用模型，提供补资料入口 |
| 样本不足 | 低于该场景的明确最低门槛 | 不生成团队/经营结论，显示缺口和门槛 |
| 有限样本 | 达到最低门槛但稳定性不足 | 可生成趋势，必须突出限制，不显示精确归因 |
| 样本充分 | 达到已定义的业务门槛 | 允许生成，仍保留“AI 推断”标签 |
| 已过期 | 关键事实或样本在生成后变化 | 不允许直接采纳，要求刷新或重新生成 |

门槛由具体业务规则定义并在界面公开，不使用一个全局数字。销售辅导继续采用现有规则：
少于 10 个已观察客户为“样本不足”，10–29 为“有限样本”，30 及以上为“样本充分”。
报价、订单或团队对标等指标的分母为 0 时显示“暂无样本”，不得显示 `0%` 暗示真实转化率。

客户级评分使用“资料覆盖”而不是“团队样本量”，至少列出已覆盖、缺失和受限的关键字段。
全局页面必须显示“已分析数量 / 可分析总数”，不能用 15 个结构化结果代表 1902 个客户。

### 7.6 能力的业务含义与副作用

8 个工作站继续保留其服务端能力，但只作为内部能力标识；业务页面使用用户能理解的名称：

| 内部能力 | 用户看到的含义 | 输入 | 默认结果 | 允许的业务动作与副作用 |
|---|---|---|---|---|
| customer_fit | 是否值得优先开发 | 客户资料、产品与情报证据 | 适配判断、理由、缺口 | 仅供排序和判断；不改变客户状态、分组或负责人 |
| contact_readiness | 是否具备可联系条件 | 联系人身份、任职与联系方式证据 | 就绪程度和缺失项 | 进入人工复核；不自动认定联系人有效 |
| distribution_priority | 哪些线索应先分配 | 规则资格、风险和证据覆盖 | 优先级建议 | 经理确认前不分配、不改优先级 |
| sales_match | 更适合由谁跟进 | 服务端给定的候选销售与范围内指标 | 候选排序和理由 | 经理选择后才执行分配；AI 不扩展候选范围 |
| sales_pack | 开发前参考资料 | 客户、联系人、情报和权限内事实 | 摘要、切入点、沟通草稿 | 可复制或编辑；绝不自动发送、不写客户状态 |
| next_action | 接下来建议做什么 | 最近业务事件和当前 CRM 状态 | 动作、时间和理由 | 修改或采纳后才写入待办/下一步；生成本身不写 CRM |
| manager_anomaly | 为什么出现规则异常 | 服务端已识别的确定性异常 | 解释、优先级和介入建议 | AI 不创建异常、不改状态、不重新分配；经理确认后另行操作 |
| sales_coaching | 该如何辅导销售 | 权限范围内的聚合结果和 SLA 指标 | 趋势、差距和建议 | 仅供经理复核；样本不足不调用模型，不作为绩效定论 |

`action_proposal` 是快速更新中的辅助流程：AI 可以把用户输入整理为活动草稿，但必须在
确认界面展示最终活动类型、摘要、下一步和阶段变化，人工确认后才写入活动。

资料补全是受控工作流，不等于 AI 自动修改客户：

- 搜索和归集结果先成为带来源、时间和置信信息的候选事实。
- 官网、国家、行业、客户类型、产品需求、评级和客户分组等关键字段以提案形式呈现。
- 接受前显示旧值、新值、依据和影响；逐项人工确认后才写入。
- 拒绝保留审计，不继续污染客户主数据。
- 联系人相关字段继续遵循敏感权限、身份核验和人工复核要求。

### 7.7 页面与角色落位

AI 不再作为一组平级业务页面。它在用户当前工作的页面中出现：

| 业务位置 | AI 提供的辅助 |
|---|---|
| 我的今日 | 已采纳的下一步、待本人复核的建议；未采纳建议不算正式待办 |
| 我的客户 / 客户详情 | 值得开发判断、资料覆盖、销售资料包、补全提案和证据 |
| 线索分配 | 确定性资格与风险在前，AI 优先级和销售匹配在后，经理最终裁决 |
| 快速更新 | 活动草稿与下一步建议，确认后才落库 |
| 经理今日待办 | 规则异常在前，AI 解释与介入建议在后 |
| 团队洞察 | 真实聚合指标在前，达到样本门槛后再提供 AI 辅导 |
| AI 助手 | 明确当前客户或团队 scope 的问答入口，不替代业务写入表单 |

销售不显示 AI 任务中心。经理只在拥有 `review_ai_tasks` 权限且处理待复核或故障时，通过
业务结果的次级“运行记录”入口查看授权范围内的任务，不将其放在日常一级导航。管理员在
“系统管理 > AI 运行审计”查看全局任务、模型尝试、成本、预算、fallback、复核和
decision trace。

模型、Prompt、影子版本、发布批准、回滚、引擎和 AI feature flags 统一归入
“系统管理 > AI 治理”，只允许管理员访问。经理不再拥有策略发布和回滚能力。

### 7.8 降级原则

- AI 不可用时，事实、规则、历史结果和人工流程保持可用。
- 历史 AI 结果必须显示生成时间和过期状态，不伪装成当前事实。
- 生成失败时解释业务影响，并提供人工路径；普通用户不需要理解 Worker 或 fallback。
- AI 结果不能作为领取、分配、跟进、报价、订单或客户状态变化的隐式前置条件。

## 8. 错误处理

| 状态 | 前端行为 |
|---|---|
| 401 | 清理会话相关状态并返回登录页 |
| 403 | 不渲染入口；深链显示无权限状态并回角色首页 |
| 404 | 显示对象不存在或已不可见，不保留失效详情 |
| 409 / stale | 告知数据已变化，刷新权威数据后要求用户重新确认 |
| 422 | 在具体字段或操作区显示服务端校验信息 |
| 网络 / 5xx | 保留已加载数据，模块内显示重试，不清空整个工作区 |
| AI 失败 | 展示规则回退和人工路径，不阻断 CRM |

错误消息继续使用服务端脱敏摘要，不展示 Prompt、密钥、完整任务输入、租约或 Worker 内部字段。

## 9. 响应式与可访问性

### 9.1 响应式

- 桌面继续使用侧栏和高密度工作区。
- 780px 以下不保留窄侧栏 + 窄主栏结构。
- 销售移动端使用 4 个主入口；经理和管理员显示高频入口与“更多”菜单。
- 数据表使用稳定的横向滚动容器和边缘提示；关键动作保持可见。
- 客户详情在移动端改为全页，tab 可横向滚动，不使用覆盖大部分视口的窄抽屉。
- 弹窗内容区滚动、操作区吸底。
- 390px 验收要求 `documentElement.scrollWidth === clientWidth`，明确允许横向滚动的数据表除外。

### 9.2 可访问性

- 所有图标按钮和开关有可访问名称。
- modal 和 drawer 使用正确 dialog 语义、焦点进入、焦点恢复和 Esc 关闭。
- tab、segmented control、菜单和通知状态具备对应 ARIA 状态。
- 颜色不能作为风险、AI 或状态的唯一表达。
- 键盘可完成导航、筛选、打开详情、切换 tab 和关闭弹层。

## 10. 渐进迁移

### 阶段 0：功能资产与回归基线

- 固定启动 SHA、生产 SHA 和功能并集。
- 建立迁移追踪矩阵。
- 记录三角色导航、页面、深链、权限、API、Worker 和发布基线。
- 固定 AI 真实性、覆盖率、触发来源和副作用基线，历史来源缺失标为 `legacy_unknown`。
- 补齐缺失的契约测试后才开始拆分。

### 阶段 1：核心层抽取

- 抽出 API、状态、访问控制、路由和生命周期。
- 抽出 modal、drawer、table、empty-state 和 AI 结果组件。
- 统一 AI 结果、触发来源、证据、覆盖状态和动作副作用的前后端合同。
- 保持现有页面、URL 和视觉不变。
- 完整回归通过后合并。

### 阶段 2：角色外壳与首页

- 注册表生成导航。
- 上线销售“我的今日”和角色默认首页。
- 合并重复导航入口，保留旧 hash 别名。
- 旧渲染器继续承载尚未迁移的页面。

### 阶段 3：核心经营工作流

- 迁移线索、客户列表、当前阶段管道、预警、通知和快速更新。
- 完成漏斗累计口径和列表当前口径。
- 所有预警在两步内到达处理动作。

### 阶段 4：统一客户详情

- 迁移完整资料、联系人、跟进、商务、Recon、评价、标签和 AI。
- 通过 iframe 退役门后删除 iframe。
- 保留旧深链兼容。

### 阶段 5：管理与 AI

- 迁移团队洞察、情报中心、用户权限、回收站和维护。
- 迁移 AI 运行审计、预算、反馈、策略治理、decision trace 和引擎控制。
- 将 AI 治理权限收紧到管理员；经理只保留授权范围内的结果复核与故障查看。
- 完成 8 个内部能力的业务落位、真实性标签、覆盖门槛和运行详情跳转。

### 阶段 6：模块搭建与质量收口

- 上线角色默认布局和用户布局偏好。
- 权限和 feature flag 优先于偏好。
- 完成移动端、键盘和可访问性。
- 完成全功能等价审计。

### 阶段 7：切换与退役

- 临时发布开关切换到新外壳。
- 完成生产备份、quick_check、local/public health、三角色和 390px smoke。
- 保留一个明确回滚 release。
- 稳定观察期通过后删除旧外壳和临时发布开关。
- 将 `ux-preview` 标记为只读历史参考并停止维护。

## 11. 临时发布开关

`CRM_UX_REDESIGN_ENABLED` 只控制新旧前端外壳，不控制任何业务功能。

- 关闭：使用旧导航和旧页面组合。
- 开启：使用新注册表、角色首页和模块组合。
- 两种外壳调用相同 service、API 和业务规则。
- 迁移期旧路由别名在两种外壳中都有效。
- 全量切换稳定后删除该开关，避免永久维护双外壳。

## 12. 测试与验收

### 12.1 每阶段必过

- 新增模块的 `node:test` 单元和合同测试。
- 受影响的权限、API、AI、通知和业务流程测试。
- 完整 `npm test`，不得减少既有通过项。
- `node --check` 覆盖全部新增和修改 JavaScript。
- `git diff --check`。

### 12.2 浏览器矩阵

角色：

- 管理员
- 经理
- 销售

视口：

- 桌面 1440px
- 常规桌面 1280px
- 移动端 390px

行为：

- 登录和默认首页
- 所有可见导航
- 旧深链和新深链
- 前进、后退和刷新
- 搜索、分页、筛选、导出
- 客户详情全部 tab
- 关键写入和确认
- AI 开启、关闭、失败和 stale
- AI 触发来源、证据、覆盖状态、事实与推断标签
- AI 生成、采纳、修改后采纳和拒绝的副作用确认
- 无权限和身份检查
- 无控制台错误
- 无页面级横向溢出或控件遮挡

### 12.3 功能等价门

每个迁移矩阵条目必须同时具备：

1. 新入口或明确的归并位置。
2. 相同或更严格的角色、权限和行级范围。
3. 相同业务 API 或经批准的兼容 API。
4. 正常、空、错误和无权限状态。
5. 自动化测试证据。
6. 浏览器验收证据。
7. 旧入口的保留、别名或退役决定。

### 12.4 AI 决策安全门

以下自动化测试和浏览器验收全部通过前，AI 页面不得切换到新外壳：

1. 评分、资料包、异常解释和销售辅导的“生成”不会改变客户状态、负责人、阶段或活动。
2. 销售资料包不会调用发送接口，也不会创建外发通知或消息。
3. 下一步建议只有人工确认后才写入 `next_action` 和 `next_action_at`；未采纳建议不进入待办。
4. 活动提案只有确认后才创建活动，并在确认前展示所有字段和阶段副作用。
5. 补全提案只有逐项接受后才更新关键字段，拒绝和 stale 均不写主数据。
6. 经理异常必须来自确定性规则；AI 不能自行创建异常或重新分配客户。
7. 销售辅导少于 10 个已观察客户时不调用模型，分母为 0 的指标显示“暂无样本”。
8. 每个新 AI 任务都有权威 `trigger_source`；业务事件和 workflow 可反查，历史任务显示
   `legacy_unknown`。
9. 所有结论区分来源事实、确定性规则、AI 推断和人工决定；权限受限证据不泄露。
10. 普通销售不能访问任务中心；经理不能访问模型和版本治理；管理员保留完整审计能力。

## 13. 回滚

- 每个阶段独立 PR、独立完整回归、独立生产发布。
- 数据库迁移与纯前端迁移分离；无必要不新增数据库迁移。
- 新外壳异常时关闭临时发布开关，回到同一 release 中的旧外壳。
- release 异常时使用现有 `previous` 完整回滚。
- 不自动恢复数据库；涉及数据库时继续遵循现有手工恢复边界。

## 14. 风险与控制

| 风险 | 控制 |
|---|---|
| 重构遗漏隐藏功能 | 功能并集、迁移矩阵、三角色遍历和旧路由清单 |
| `app.js` 拆分时行为变化 | 先抽取后改 UI，每个抽取阶段完整回归 |
| 新旧状态不同步 | 两种外壳共用 store、service 和 API，不复制业务状态 |
| 轮询和事件泄漏 | 统一 lifecycle 和强制 `dispose` |
| iframe 过早删除 | 独立 iframe 退役门 |
| 移动端再次退化 | 390px 每阶段验收，不留到最后一次修复 |
| AI 功能被导航收敛隐藏 | 每个内部能力都有业务落位和迁移矩阵，不依赖独立工作站页面 |
| AI 推断被误认为事实 | 固定四层标签、证据引用、覆盖状态和过期提示 |
| 不清楚结果为什么出现 | 强制触发来源合同；历史缺失明确显示，不由前端推测 |
| 低覆盖产生虚假确定性 | 展示已分析/可分析数量；按场景执行样本门槛 |
| AI 动作产生隐式副作用 | 确认前展示写入清单，并用服务端测试证明生成阶段只读 |
| 治理能力暴露给业务角色 | 治理仅管理员；任务中心从日常导航下沉到审计和故障入口 |
| 永久维护两套外壳 | 临时开关有明确删除阶段和完成条件 |

## 15. 完成定义

只有同时满足以下条件，前端重构才算完成：

1. 功能迁移矩阵无未映射、未测试或未决定条目。
2. 实施基线中的全部正式能力在新外壳中可达。
3. 三角色权限和客户范围无扩大、无泄露。
4. 旧深链有兼容行为。
5. 客户详情 iframe 已通过退役门并删除。
6. 8 个 AI 内部能力和 AI 补全均在对应业务流程中完整可达，不要求用户理解工作站名称。
7. 每个 AI 结果可解释触发来源、事实依据、推断、覆盖、限制、动作和副作用。
8. 历史来源缺失被诚实标记，新任务不存在来源缺失。
9. AI 任务中心按角色下沉，模型与版本治理仅管理员可达。
10. AI 故障不阻断 CRM 人工流程，生成动作不会隐式改变业务状态或自动外发。
11. 桌面和 390px 无页面级横向溢出、遮挡或不可操作控件。
12. 完整自动化回归、浏览器回归、生产 smoke、备份和回滚验证通过。
13. 临时发布开关和旧外壳已删除。
14. `ux-preview` 已停止作为并行产品维护。
