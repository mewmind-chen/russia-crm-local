# 五项客户侧栏与不对口流程改进设计

## 1. 目标

完成以下五个 GitHub Issues，同时保持客户身份、权限范围、历史状态和生产发布链路稳定：

- [#283 修复不对口记录列表错位并恢复完整客户资料入口](https://github.com/mewmind-chen/russia-crm-local/issues/283)
- [#284 移除普通阶段中的确认不对口，统一走专用不对口流程](https://github.com/mewmind-chen/russia-crm-local/issues/284)
- [#285 优化客户侧栏资料卡布局：简介全宽，产品与来源并排](https://github.com/mewmind-chen/russia-crm-local/issues/285)
- [#286 优化 CRM 客户侧栏摘要：去重行业类型并统一官网链接](https://github.com/mewmind-chen/russia-crm-local/issues/286)
- [#287 客户侧栏下一步动作增加克制的相对倒计时](https://github.com/mewmind-chen/russia-crm-local/issues/287)

本设计只覆盖上述五项需求，不扩展审批、通知、自动回收、经理介入或全站视觉改版。

## 2. 基线与约束

- 设计基线：`origin/main` at `3d034eed602e664133d578033d6e5b7090d6d0a9`。
- 保留 `disqualified` 历史机器值，继续支持历史查询、筛选、统计、时间线和导出。
- 不迁移、不复制、不重建现有客户数据。
- 不改变稳定客户编号、CRM account ID、intake ID 和现有审计身份。
- 所有权限判断必须由服务端执行；前端按钮可见性不能替代授权校验。
- 只读查看不得恢复客户、创建 CRM account、重新分配客户或写入业务审计。
- 客户侧栏调整不增加任何账号的客户可见范围。
- 时间计算复用现有业务时区和 UTC 存储语义。
- 前端不引入新依赖，继续使用现有原生 JavaScript、HTML 和 CSS。
- 每个交付批次必须通过专项测试、完整测试、GitHub CI、生产自动部署和双端发布门禁。

## 3. 方案比较与决策

### 方案 A：三个 PR 逐批上线（采用）

1. #284 收口不对口写入入口。
2. #283 补齐不对口记录读取闭环。
3. #285、#286、#287 完成客户侧栏 UI。

优点：写入、读取和纯展示的风险边界清晰；每批可以独立回滚；同一侧栏的三个 UI Issue 在一个 PR 内避免重复冲突和缓存更新。

### 方案 B：两个 PR

把 #283 与 #284 合为一个不对口流程 PR。提交数量更少，但权限读取和业务写入耦合，失败时难以定位和回滚，因此不采用。

### 方案 C：五个 PR

每个 Issue 独立交付。追踪最细，但 #285、#286、#287 会连续修改同一侧栏渲染和样式，产生重复冲突、重复缓存版本和重复部署，因此不采用。

## 4. 总体交付顺序

### PR 1：#284 不对口写入入口收口

先阻止新的不一致记录产生，再处理历史记录的读取体验。

### PR 2：#283 不对口记录详情闭环

统一领取前 intake 记录与领取后 account 记录的只读查看路径。

### PR 3：#286 → #285 → #287 客户侧栏 UI

先删除重复字段，再确定三卡布局，最后加入相对时间组件；三项完成后只更新一次静态资源缓存版本。

每个 PR 合并并通过生产验收后，才开始下一个 PR。

## 5. PR 1 设计：唯一不对口写入路径

### 5.1 业务边界

`disqualified` 不再是普通推进阶段，而是必须填写原因并进入“不对口记录”的独立终止动作。

普通客户编辑和主管任务只允许普通推进阶段或 `lost`。唯一合法的不对口写入入口是现有专用“标记不对口”接口。

### 5.2 数据流

```text
普通编辑客户 / 主管终止任务
        ↓
普通接口校验阶段
        ↓
只允许普通阶段或 lost
        ↓
保存普通阶段变化

标记不对口按钮
        ↓
专用 reject 接口
        ↓
原因校验 + 权限校验 + 当前状态校验
        ↓
单一数据库事务
        ↓
lifecycle / recycle / intake / audit 同步更新
        ↓
客户进入不对口记录
```

### 5.3 前端

- “编辑客户资料”的阶段下拉框过滤 `disqualified`。
- 主管“正式终止跟进”只提供 `lost`，不再提供“不合格客户”。
- 独立“标记不对口”按钮和原因填写流程继续保留。
- 专用操作成功后刷新 CRM 客户列表、不对口记录、侧栏计数和相关待办。
- 专用操作失败时显示服务端真实错误，前端不得提前移除客户。

### 5.4 后端

- `updateAccount()` 收到 `stage=disqualified` 时返回 `400`，中文提示用户使用专用不对口操作。
- `managerTaskChange()` 的 `terminal_stage` 只接受 `lost`。
- `rejectCrmCustomer()` 保持唯一合法的不对口写入路径。
- 专用事务任一步失败时整体回滚，不允许只修改阶段或只写入部分回收状态。
- `STAGES` 和历史读取逻辑继续识别 `disqualified`。

### 5.5 错误语义

- 普通入口写入 `disqualified`：`400`。
- 当前账号无不对口操作权限：`403`。
- 客户不存在：`404`。
- 客户已回收或当前状态不可操作：`409`。

## 6. PR 2 设计：统一不对口记录详情

### 6.1 稳定记录身份

继续使用现有 `recordKey` 区分来源：

- `account:<accountId>`：领取进入 CRM 后标记不对口。
- `intake:<intakeId>`：领取前在线索池标记不对口。

前端不得再用“是否存在 CRM customerId”决定记录能否打开。

### 6.2 数据流

```text
点击不对口记录客户名称
        ↓
读取详情(recordKey)
        ↓
服务端解析 account / intake
        ↓
按当前账号和来源执行权限校验
        ↓
组装统一只读详情 DTO
        ↓
同一侧栏组件渲染
```

### 6.3 统一只读详情模型

响应至少包含：

- `recordKey` 与 `sourceType`。
- 稳定客户编号、account ID 或 intake ID。
- 公司名称、国家、地区、官网、行业、客户类型、产品与简介。
- 不对口原因、原负责人、操作人和操作时间。
- 当前权限允许显示的联系人与联系方式。
- 来源证据与背调入口。
- 生命周期、跟进、询价、报价、订单、经理评价、审计和时间线。
- 当前账号允许执行的管理动作；普通只读查看默认不包含写操作。

对于 intake 来源，不伪造 CRM account；不存在的 CRM 历史使用空集合和明确空状态。

### 6.4 权限规则

- 销售仅能读取本人相关且在其“不对口记录”范围内可见的数据。
- 主管仅能读取团队授权范围。
- 管理员按现有全局授权范围读取。
- 记录存在但越权返回 `403`。
- 记录真实不存在返回 `404`。
- 服务端通过 `recordKey` 和当前用户重新校验，不能信任前端传入的负责人或来源类型。
- 联系方式继续执行现有权限脱敏，不借详情接口泄露其他销售数据。

### 6.5 前端交互

- 不对口记录第一列的表头、客户名称、编号和国家统一左对齐。
- 客户名称是明确可点击入口；行内下拉框和操作按钮不触发打开详情。
- 打开后先显示“正在读取完整客户资料”。
- 快速切换记录时使用请求序号，旧响应不能覆盖新侧栏。
- `403` 显示无权提示并关闭无效详情。
- `404` 提示记录已变化并刷新列表。
- 网络失败不清空列表、筛选和分页，用户可重试。
- 无联系人、无历史、无审计时显示“暂无……”空状态，不显示空白横线。
- 关闭详情返回列表后保留筛选、分页和授权总数。

## 7. PR 3 设计：客户侧栏 UI

### 7.1 #286 摘要去重与官网链接

- 侧栏顶部继续显示客户编号、国家、城市、行业和客户类型。
- “企业背景与开发依据”删除重复的“行业与客户类型”卡片。
- 完整客户资料页仍保留行业和客户类型明细。
- 官网事实使用现有 `websiteMarkup()` 规范化和渲染。
- 只允许 HTTP/HTTPS 链接，使用新标签页和 `noopener`。
- 空官网显示统一空值，危险或无法识别的值不生成链接。
- 普通事实值继续按纯文本转义，不能为支持官网 HTML 而放宽所有字段的转义。

### 7.2 #285 三卡布局

删除重复字段后，剩余三张卡按以下布局：

- 第一行：企业简介横跨整行。
- 第二行：产品与潜在需求、背调与来源左右并排。
- 卡片按内容自然增长，不设置制造空白的固定高度。
- 窄侧栏和手机端按企业简介、产品、来源顺序切换为单列。
- 长简介、长产品和长来源文本自然换行，不产生横向滚动。

### 7.3 #287 相对时间

新增纯时间状态函数，输入计划时间、`next_action_time_basis` 和当前时间，输出：

- 状态：`normal`、`approaching`、`dueSoon`、`overdue` 或 `unavailable`。
- 相对文案。
- 准确计划时间。
- 读屏文案。

显示规则：

- 剩余时间大于等于 48 小时：显示完整天数 `还有 N 天`；不足一天的余数不展示。
- 剩余时间大于 24 小时且小于 48 小时：显示 `还有 1 天 N 小时`。
- 剩余时间大于 1 小时且小于等于 24 小时：向上取整显示 `还有 N 小时`，避免出现 `还有 0 小时`。
- 剩余时间大于 0 且小于等于 1 小时：向上取整显示 `还有 N 分钟`。
- 差值等于 0：显示 `已到计划时间`。
- 差值小于 0：按同一粒度显示 `已超时 N 分钟 / N 小时 / N 天`，最小显示 `已超时 1 分钟`。

视觉规则：

- 剩余时间大于 24 小时使用品牌色或中性色，不显示警告图标，状态为 `normal`。
- 剩余时间大于 6 小时且小于等于 24 小时使用克制的琥珀色，状态为 `approaching`。
- 剩余时间大于等于 0 且小于等于 6 小时继续使用琥珀色，可略加强字重，不使用红色警报，状态为 `dueSoon`。
- 只有逾期相对文案使用克制的危险色。
- 不显示秒数、进度条、闪烁、脉冲或整卡红色。
- 准确时间始终作为次级信息保留。

时间与生命周期规则：

- 只有 `next_action_time_basis=utc` 时生成可靠相对时间。
- 历史时间依据不明确时显示准确时间和“历史时间待确认”，不生成倒计时。
- 空值或无效时间显示“尚未安排时间”。
- 侧栏打开时按分钟更新；关闭时清理定时器。
- 浏览器标签重新可见时立即重算，不在后台执行高频刷新。
- 编辑计划或记录新进展后立即按最新计划重算。

### 8.2 PR 2

- 本人销售：`200`。
- 其他销售：`403`。
- 授权主管：`200`。
- 非授权主管：`403`。

同时验证：

- 查看前后业务数据无变化。
- 稳定 ID 不变。
- 空联系人、空时间线、空审计显示正确。

- 回归 #137、#273 以及恢复、重新分配和审计流程。

### 8.3 PR 3

官网输入覆盖：

- 完整 HTTPS。
- 无协议域名。
- 带路径地址。
- 超长地址。
- 空值。
- `javascript:` 等危险值。

相对时间使用固定时钟覆盖：

- 49 小时、36 小时、12 小时、5 小时、59 分钟。
- 正好到期、逾期 1 分钟、逾期 26 小时。
- UTC、历史时间、无效时间和空计划。
- 打开、关闭、重复打开、编辑计划和浏览器标签恢复。

布局覆盖：

- 桌面侧栏简介全宽。
- 产品与来源并排。
- 窄屏单列。
- 长内容不溢出。
- 无重复行业卡和无空白占位。
- 销售、主管、管理员授权视角一致。

## 9. 发布与回滚

每个 PR 独立执行：

1. 从最新 `origin/main` 创建隔离 worktree。
2. 先写失败测试，再做最小实现。
3. 运行专项测试、语法检查、差异检查和完整测试。
4. 推送分支并创建关联 Issue 的 PR。
5. 等待 GitHub CI 全部通过。
6. Squash 合并。
7. 等待生产自动部署完成。
8. 校验生产 release SHA。
9. 运行本机与公网发布门禁。
10. 使用销售、主管、管理员身份做生产只读验收。
11. 确认关联 Issue 关闭并记录部署结果。
12. 开始下一个 PR。

任何一批失败都停止后续批次。生产继续由版本化 release 目录和 `current` / `previous` 指针管理；回滚使用上一完整 release，不手工覆盖生产文件。

## 10. 明确非目标

- 不新增不对口审批流程。
- 不新增企微催办、通知、弹窗或经理任务。
- 不改变领取后首次触达的 48 小时业务规则。
- 不自动退回、升级或重新分配逾期客户。
- 不把其他页面的日期全局改成倒计时。
- 不对不相关页面进行视觉重构。
- 不清理或转换历史 `disqualified` 数据。
- 不改变导出字段和稳定机器值。
