# CRM 权限组、多管理员与身份检查设计（Issue #3）

## 目标与范围

本设计在现有 Node.js、Express、SQLite 和服务端 session 架构上补齐四项能力：

1. 支持多个管理员，并允许管理员编辑用户姓名、角色、状态和权限归属。
2. 用权限组作为账号的默认权限来源，同时允许对单个用户做“继承 / 强制允许 / 强制拒绝”覆盖。
3. 允许管理员为其他用户设置正式新密码，并立即注销该用户的旧会话。
4. 允许管理员临时以经理或销售的真实权限和数据范围检查系统，且审计可区分真实管理员和有效用户。

系统预计不超过 20 名用户，因此继续使用 SQLite，不引入外部身份服务、Redis、复杂 RBAC 产品或组织层级。Issue #4 已建立的集中访问控制和行级范围仍是最终安全边界；本设计扩展其权限来源和请求身份，不绕开已有策略。

Recon 执行耗时较长，身份检查期间第一版全面禁止启动 Recon 和联系人 Recon。权限组第一版不支持删除，以避免迁移、在用组和审计引用的额外复杂度。

## 已确认的设计选择

采用“角色安全边界 + 权限组默认值 + 用户三态覆盖”的组合模型。

- `admin / manager / sales` 角色保留，代表身份级安全边界和可被代入的身份类别。
- 每个用户必须且只能属于一个权限组。
- 权限组定义每项权限的默认布尔值。
- 用户级权限为三态：继承组默认值、强制允许、强制拒绝。
- 有效权限先读取组默认值，再应用用户覆盖；强制允许和强制拒绝都被支持。
- 现有 `permissions_json` 迁移为用户覆盖，保留旧字段用于紧急回滚，但运行时不再读取。

不采用“每个用户单独保存完整权限”的现状延伸，因为账号增多后难以保持一致；也不采用“组权限不可覆盖”，因为老板仍需要针对单个人临时收紧或开放能力。

## 数据模型与迁移

### 1. 权限组

新增 `permission_groups`：

- `id`：稳定 ID。
- `name`：唯一、非空的显示名称。
- `description`：可选说明。
- `role_key`：`admin / manager / sales`，限定该组可分配给哪类角色。
- `permissions_json`：覆盖所有已知权限 key 的布尔对象。
- `system_key`：默认组使用的稳定标识，普通自定义组为空。
- `created_at / updated_at`。

`role_key` 防止把销售用户放进管理员组后误以为其已成为管理员，也防止角色变更后继续沿用不匹配的默认权限。用户角色变化时必须同时选择同角色的目标组；接口不做隐式猜测。

### 2. 用户归组

为 `sales_users` 增加非空 `permission_group_id` 外键语义。SQLite 迁移期间先允许空值，完成默认组创建和用户回填后，应用层把“每个用户必须有组”作为写入不变量。所有创建和编辑入口必须校验组存在且 `role_key` 与用户角色一致。

### 3. 用户三态覆盖

新增 `user_permission_overrides`：

- `user_id`。
- `permission_key`。
- `effect`：仅允许 `allow` 或 `deny`。
- `created_at / updated_at`。
- `(user_id, permission_key)` 唯一。

“继承”不存一行；将某项改回继承即删除该覆盖行。未知权限 key、重复 key 或其他 effect 值必须拒绝。读取时只返回当前 `PERMISSION_DEFINITIONS` 中存在的 key。

### 4. 迁移规则

迁移必须在同一数据库事务内完成：

1. 按当前 `ROLE_PERMISSIONS` 创建系统默认管理员、经理、销售三个组。
2. 按用户现有角色分配对应默认组。
3. 对每个用户解析现有 `permissions_json`。
4. 仅当旧值与该角色默认值不同，才创建 `allow` 或 `deny` 用户覆盖。
5. 迁移后逐用户比较迁移前、迁移后的完整有效权限对象；任一不一致则回滚事务并停止启动。

`sales_users.permissions_json` 暂不删除、不清空，也不再由运行时代码读取或写入。这样数据库可回滚到旧版本，但新版本只有权限组和覆盖表是权威来源。

迁移必须可重复执行：已存在的系统组按 `system_key` 复用，不重复创建；已经完成回填的用户不重复生成覆盖。

## 有效权限与安全不变量

### 1. 有效权限计算

集中访问控制模块提供唯一的权限解析入口：

1. 读取用户及其当前权限组。
2. 校验用户启用、组存在且组角色与用户角色相同。
3. 以组的完整权限对象为默认值。
4. 按用户覆盖逐项替换为 true 或 false。
5. 对缺失或未知权限默认拒绝。

`sessionUser()` 每次请求仍从数据库读取用户，并在同一请求中解析组和覆盖，因此管理员修改组权限、个人覆盖、角色或状态后，已有 session 的下一次请求立即使用新结果，不依赖重新登录或缓存失效。

角色不是权限快捷方式。除“谁可以启动身份检查”等明确的身份级规则外，业务路由继续通过有效权限判断。用户角色和组必须匹配，不能用个人覆盖绕过该约束。

### 2. 有效管理员定义

“有效管理员”必须同时满足：

- `sales_users.active = 1`；
- `role = 'admin'`；
- 有效权限中 `view_users = true`；
- 有效权限中 `manage_users = true`。

系统在任何相关写操作提交前，使用拟议变更后的状态重新计算全体用户，保证至少存在一个有效管理员。保护覆盖：

- 用户角色变更；
- 用户启用或停用；
- 用户更换权限组；
- 管理员组的权限修改；
- 管理员个人覆盖修改。

检查必须和写入处于同一 SQLite 事务，不能先检查后在事务外修改。即使修改的对象不是当前操作者，只要结果会使有效管理员数量归零就返回 409。普通权限不足仍返回 403。

第一版允许多个有效管理员，也允许管理员修改自己的组或覆盖；只要事务后的有效管理员数量不为零即可。

## API 与服务边界

账号资料、用户覆盖、权限组、管理员改密和身份检查使用分离端点，避免一个通用 PATCH 同时处理安全含义不同的字段。

### 1. 用户账号

- `POST /api/sales-crm/users`：创建用户，要求 `view_users + manage_users`；必须提供角色、同角色权限组和管理员设置的正式密码。
- `PATCH /api/sales-crm/users/:userId`：只编辑姓名、角色、组和启用状态；要求 `view_users + manage_users`。
- 用户角色变化时，payload 必须同时提供与新角色匹配的组。
- 新建用户写入 `must_change_password=0`，不强制首次登录改密。

### 2. 用户权限覆盖

- `PUT /api/sales-crm/users/:userId/permission-overrides`：一次提交该用户全部三态值，要求 `view_users + manage_users`。
- `inherit` 删除覆盖，`allow` 写入允许，`deny` 写入拒绝。
- 服务端忽略任何前端推导结果，提交后重新计算有效权限和最后管理员不变量。

### 3. 权限组

- `POST /api/sales-crm/permission-groups`：创建自定义组，要求 `view_users + manage_users`。
- `PATCH /api/sales-crm/permission-groups/:groupId`：修改名称、说明和默认权限，要求 `view_users + manage_users`。
- `GET /api/sales-crm/permission-groups`：返回组、默认权限和成员数量，要求 `view_users`。
- 第一版没有删除或停用端点。
- 修改组后，所有成员的下一次请求立即按新权限执行；若会破坏最后管理员不变量，整个修改返回 409。

### 4. 管理员重置密码

- `POST /api/sales-crm/users/:userId/password-reset`，要求 `view_users + manage_users` 且真实操作者角色为 `admin`。
- 该端点只用于重置其他用户；管理员修改自己的密码继续使用本人改密端点。
- 请求包含 `password` 和 `passwordConfirm`；服务端要求二者一致并执行现有密码强度校验。
- 事务内写入新的 scrypt 哈希和盐，设置 `must_change_password=0`，删除目标用户全部 `sales_sessions`。
- 旧密码和旧 session 立即失效；响应、审计和错误日志不得包含密码、哈希或盐。

本人修改密码继续使用现有身份端点和规则，不与管理员重置端点混用。身份检查期间禁止任何本人或他人的密码修改。

## 身份检查模型

### 1. 会话表示

真实管理员身份继续由现有 `sales_sessions.user_id` 保存，不把 session 改写为目标用户。为 session 增加可空的身份检查状态：

- `impersonated_user_id`：目标用户。
- `impersonation_started_at`。
- `impersonation_expires_at`。
- `impersonation_context_id`：每次开始生成的不可预测 ID，用于关联审计事件。

默认有效期为 30 分钟，不提供延长接口。重新开始必须先正常结束当前身份检查，禁止嵌套代入。

### 2. 启动与结束

- `POST /api/sales-crm/impersonation/start`：仅真实用户为启用状态的 `admin`，且有效权限具备 `view_users + manage_users` 时允许。
- 目标只能是启用状态的 `manager` 或 `sales`，不能是管理员本人、其他管理员或停用用户。
- `POST /api/sales-crm/impersonation/stop`：清空当前 session 的代入字段，并记录结束事件。
- 普通经理、销售或已经处于身份检查状态的请求调用启动端点一律返回 403。

启动和结束只影响发起操作的管理员 session，不影响目标用户自己的 session、密码和登录状态。

### 3. 请求身份解析

每个受保护请求解析两个身份：

- `realUser`：session 对应的真实管理员或普通登录用户。
- `effectiveUser`：无身份检查时等于 `realUser`；身份检查有效时为目标用户。

业务授权、菜单能力、客户行级范围和普通业务写操作全部使用 `effectiveUser` 的当前角色、当前权限组和当前个人覆盖。若管理员在检查期间修改了目标的组或覆盖，下一请求立即生效。

以下情况必须在进入路由业务逻辑前终止身份检查并拒绝本次请求：

- 当前时间达到或超过 `impersonation_expires_at`；
- 目标用户已停用、不存在、角色变为 admin；
- 目标用户的组丢失或与角色不匹配。

服务端先清空 session 的代入字段、记录 expiry/invalidated 审计，再返回 `409` 和稳定错误码 `IMPERSONATION_ENDED`，要求前端刷新管理员状态。本次原始请求绝不能回落为管理员身份继续执行。真实管理员 session 仍然有效，刷新后的新请求恢复管理员身份。

### 4. 身份检查期间允许与禁止的操作

允许目标用户本来就有权限执行的普通业务操作，包括：客户创建或编辑、跟进记录、报价、订单、联系人操作和 intake 操作。所有行级范围继续按目标用户计算。

无论目标用户有效权限如何，身份检查上下文都额外禁止：

- 启动 Recon；
- 启动联系人 Recon；
- 用户、角色、权限组和个人覆盖管理；
- 管理员重置密码和本人改密；
- 启动另一次身份检查；
- 任何只允许真实管理员执行的安全设置。

这些禁止项在集中策略层通过 `isImpersonating` 明确判断，不能仅隐藏前端按钮。被拒绝的 Recon 请求不得创建任务、记录或后台进程。

## 前端交互

### 1. 用户与权限页面

用户表格显示：姓名/邮箱、角色、权限组、个人覆盖数量、状态和操作。

管理员可执行：

- 编辑账号；
- 配置个人权限；
- 修改密码；
- 以该用户身份检查（仅经理和销售）；
- 启用或停用。

“编辑账号”表单在修改角色时同步要求选择新角色可用的权限组。修改密码表单使用两次密码输入，不展示现有密码。

### 2. 权限组管理

“用户与权限”页面增加权限组视图，显示组名、适用角色、成员数量和权限摘要。支持创建与编辑，不显示删除操作。

个人权限编辑器对每项权限使用三态控件：继承、允许、拒绝。旁边显示当前组默认值和最终有效值，避免管理员把“继承”误认为“拒绝”。保存请求只提交三态覆盖，不提交前端计算的最终权限。

### 3. 身份检查提示

身份检查开始后，所有 CRM 页面顶部持续显示不可关闭的醒目横幅，包含：

- 目标用户姓名与角色；
- 剩余时间；
- “返回管理员账号”按钮。

横幅不依赖当前子页面，导航后仍保留。倒计时归零时前端停止继续提交原操作，调用或接受服务端终止结果，然后刷新为管理员界面。即使前端倒计时失效，服务端过期检查仍是最终边界。

被禁止的安全管理和 Recon 入口在身份检查期间隐藏；直接调用仍返回 403。

## 审计设计

为现有 `crm_audit_log` 增加兼容列，以记录：

- `real_user_id`：真实操作者；普通会话中等于现有 `user_id`。
- `effective_user_id`：授权和数据范围所使用的用户。
- `impersonation_context_id`：非身份检查请求为空。
- action、实体类型、匿名化实体 ID、结果和时间。

至少记录：身份检查开始、主动结束、过期结束、失效结束、权限组变更、用户覆盖变更、角色/状态/组变更、管理员重置密码，以及身份检查期间的所有成功写操作和被拒绝的高风险写操作。

审计 UI 显示“真实管理员 -> 有效用户”。密码重置审计只记录目标用户 ID 和成功/失败结果，不记录密码、哈希、盐、session token 或请求 body。普通登录和读取操作不因本功能扩大敏感日志范围。

## 错误处理与事务

- 未登录返回 401。
- 已登录但缺少权限、身份类别不允许或身份检查期间禁止的操作返回 403。
- 拟议修改会导致零个有效管理员返回 409。
- 身份检查过期或目标身份失效返回 `409 IMPERSONATION_ENDED`，并终止原请求。
- 角色和组不匹配、密码两次输入不一致、未知权限或非法三态值返回 400。
- 允许范围内目标不存在返回 404；越权目标不回显是否存在。

组、覆盖、用户安全字段和最后管理员检查必须在同一事务中完成。管理员重置密码及 session 删除也在同一事务中完成。身份检查过期处理先结束上下文并审计，再返回错误；不执行原始业务动作。

## 测试与验收

### 1. 权限组与迁移

1. 现有数据库迁移前后，每个用户每项有效权限完全一致。
2. 每个用户恰好属于一个与角色匹配的组。
3. 修改组默认权限后，成员的已有 session 下一请求立即生效。
4. 用户 `allow` 可以覆盖组的 false，用户 `deny` 可以覆盖组的 true，改回继承后恢复组默认。
5. 未知权限、非法 effect 和角色不匹配的组均被拒绝。
6. 旧 `permissions_json` 即使随后被修改，也不影响新运行时有效权限。

### 2. 多管理员与账号安全

1. 两个有效管理员均可登录并管理用户。
2. 角色、状态、组编辑、组权限编辑和个人覆盖五条路径都不能让有效管理员数量变为零。
3. 管理员可创建不强制首次改密的新用户。
4. 管理员重置密码后，旧密码登录失败、目标用户所有旧 session 失效，新密码可直接登录且 `must_change_password=0`。
5. 普通经理和销售直接调用用户、组、覆盖和管理员改密端点均返回 403。

### 3. 身份检查

1. 代入销售时，页面和直接 API 只读取该销售负责的客户；跨范围请求返回 403。
2. 代入经理时，严格使用该经理当前组、个人覆盖和客户范围。
3. 普通客户写操作成功后，审计同时记录真实管理员、有效用户和 context ID。
4. 身份检查期间所有 Recon 与联系人 Recon 启动路径均返回 403，数据库和进程中不产生任务。
5. 用户/组/覆盖、密码和嵌套身份检查端点均返回 403。
6. 非管理员不能启动身份检查；目标管理员和停用用户不能被代入。
7. 过期请求先终止身份检查并返回错误，原业务写入不发生，也不会以管理员权限执行。
8. 主动返回管理员后，同一 session 恢复真实管理员权限，目标用户 session 不受影响。

### 4. 浏览器验证

在桌面和移动宽度下截图验证：

- 权限组列表和编辑界面；
- 用户三态权限编辑器及组默认/最终值；
- 用户表的角色、组、覆盖数量与操作；
- 身份检查顶部横幅、剩余时间和返回流程；
- 销售身份下无权入口消失，直接 API 仍为 403。

测试继续使用临时 SQLite、Node 内置 test runner 和本地随机端口。生产验证使用数据库一致性副本，日志和截图不得展示真实密码、session token、哈希或盐。

## 上线与回滚

1. 在生产数据库副本执行迁移并验证迁移前后有效权限一致。
2. 部署前用 SQLite `.backup` 创建一致性备份。
3. 运行完整自动化测试和浏览器验证后部署，重启 CRM 服务并检查本机及公网健康。
4. 用两个管理员验证最后管理员保护、正式密码重置和旧 session 失效。
5. 用销售和经理各完成一次身份检查，确认范围、写入审计、Recon 禁止和返回流程。

紧急回滚时恢复旧应用版本。旧 `permissions_json` 被保留，可供旧版本读取；新表和新增列保持在数据库中不会影响旧代码。如新版本上线后已修改组或个人覆盖，回滚前必须从部署前备份恢复数据库，避免旧字段与新权限配置不一致。
