# CRM 客户回收站设计

## 背景

生产环境当前把“取消负责人”“退回线索”和“删除客户”混在了同一套客户分配操作里：

- CRM 客户全景批量选择“不分配”时，只清空 `crm_accounts.owner_id`，客户仍然属于活跃 CRM。
- 已领取客户只能重新分配给另一名销售，不能退回。
- 手工创建的客户没有删除或归档入口。
- 现有数据维护功能会删除 CRM 经营记录，不符合本次“保留客户主档和全部衍生数据”的业务要求。

本设计增加统一的“客户回收站”。销售退回和手工删除都采用软回收，不删除客户主档、CRM 客户、活动、联系人、询价、报价、订单、Recon 或研究数据。

## 目标

1. 销售可以将自己负责的活跃客户退回回收站，并填写原因。
2. 经理和管理员可以批量退回客户，并重新分配销售退回的客户。
3. 管理员可以把手工创建的客户移入回收站并恢复。
4. 回收客户从正常 CRM、管道、预警和销售统计中排除，只在回收站显示。
5. 恢复或重新分配时继续使用原 CRM 客户 ID 和完整历史数据。
6. 所有状态迁移在单一事务中完成，并写入现有审计日志。

## 非目标

- 第一版不永久删除任何客户或衍生数据。
- 第一版不清理活动、联系人、询价、报价、订单、Recon、筛选、研究或 AI 数据。
- 第一版不自动清空或定期清理回收站。
- 第一版不把空负责人解释为退回或删除。
- 第一版不允许销售恢复客户、处理他人客户或删除手工客户。
- 第一版不替代管理员数据维护模块中的测试数据重置能力。

## 术语与状态

`crm_accounts.lifecycle_status` 表示客户是否参与正常 CRM 经营：

- `active`：正常 CRM 客户。
- `recycled`：回收客户，仅在客户回收站显示。

`crm_accounts.recycle_kind` 表示本次回收的业务类型：

- `sales_return`：销售退回，等待经理重新分配。
- `manual_delete`：管理员删除手工创建客户，等待管理员恢复。

状态迁移如下：

```text
active --销售退回/经理批量退回--> recycled(sales_return)
recycled(sales_return) --经理重新分配--> active

active --管理员手工删除--> recycled(manual_delete)
recycled(manual_delete) --管理员恢复--> active
```

不允许从 `recycled(manual_delete)` 直接重新分配，也不允许从 `recycled(sales_return)` 使用“恢复手工客户”操作。

## 数据模型

### `crm_accounts` 新增字段

| 字段 | 类型 | 默认值 | 用途 |
|---|---|---|---|
| `lifecycle_status` | TEXT NOT NULL | `active` | 活跃或回收状态 |
| `recycle_kind` | TEXT NOT NULL | 空字符串 | `sales_return` 或 `manual_delete` |
| `recycle_reason` | TEXT NOT NULL | 空字符串 | 必填的退回或删除原因 |
| `recycled_by` | TEXT NOT NULL | 空字符串 | 实际执行人的 CRM 用户 ID |
| `recycled_at` | TEXT NOT NULL | 空字符串 | 回收时间 |
| `previous_owner_id` | TEXT NOT NULL | 空字符串 | 回收前负责人，用于展示和恢复 |

现有记录迁移后全部默认为 `active`。迁移不得根据 `owner_id` 或 `assignment_status` 猜测回收状态，避免把当前未分配客户错误回收。

回收时把当前 `owner_id` 保存到 `previous_owner_id`，再把 `owner_id` 设为 `NULL`。恢复或重新分配成功后清空全部回收字段，避免活跃客户携带陈旧回收信息。

### 手工创建客户识别

第一版只有同时满足以下条件的客户可以执行“手工删除”：

- `crm_accounts.intake_item_id = ''`
- 关联 `customer_pool.source_file = 'CRM手工新增'`
- `crm_accounts.lifecycle_status = 'active'`

不能只依赖界面选择的 `crm_accounts.source`，因为该字段表示“公司指派、展会、LinkedIn”等业务来源，不代表创建方式。

## 数据保留矩阵

| 数据 | 销售退回 | 手工删除 | 恢复/重新分配 |
|---|---|---|---|
| `customer_pool` 客户主档 | 保留 | 保留 | 原记录继续使用 |
| `crm_accounts` | 软回收 | 软回收 | 原 ID 激活 |
| CRM 活动 | 保留 | 保留 | 原记录继续显示 |
| CRM 联系人 | 保留 | 保留 | 原记录继续显示 |
| 询价、报价、订单 | 保留 | 保留 | 原记录继续显示 |
| 经理评价 | 保留 | 保留 | 原记录继续显示 |
| Recon、筛选和研究证据 | 保留 | 保留 | 原记录继续使用 |
| AI 任务和结果 | 保留 | 保留 | 原记录继续使用 |
| 通知 | 保留历史；停止生成活跃客户提醒 | 保留历史；停止生成活跃客户提醒 | 恢复正常提醒 |
| 审计日志 | 追加操作记录 | 追加操作记录 | 追加操作记录 |

## 业务操作

### 销售退回

销售只能退回满足以下条件的客户：

- 客户为 `active`。
- `owner_id` 等于当前销售 ID。
- 当前账号具有查看和编辑该客户的权限。
- 不处于身份模拟状态。

退回原因必填，去除首尾空格后长度为 2 至 500 个字符。

事务内执行：

1. 重新读取客户并验证状态、负责人和权限。
2. 保存 `previous_owner_id`。
3. 设置 `lifecycle_status='recycled'`、`recycle_kind='sales_return'`、原因、执行人和时间。
4. 设置 `owner_id=NULL`、`assignment_status='returned'`、`return_reason=原因`。
5. 如果存在关联 `crm_intake_items`，设置 `status='returned'`、`assigned_owner_id=''`、`return_reason=原因`，清空领取和分配截止时间，但保留 `crm_customer_id`。
6. 写入审计日志。

保留 `crm_intake_items.crm_customer_id` 是为了重新分配时恢复同一个 CRM 客户，而不是创建新记录。

### 经理批量退回

经理或管理员可以对可访问的活跃客户执行批量退回：

- 一次最多 500 个客户。
- 原因统一必填。
- 请求中任何客户不存在、无权访问、已回收或状态不允许时，整个事务失败。
- 手工创建客户也可以按“销售退回”进入待重新分配，但不会变成“手工删除”。

现有“批量设置负责人”只接受有效销售负责人，不再使用空值表示退回。界面提供独立的“批量退回”按钮。

### 重新分配销售退回客户

经理或管理员从回收站选择有效在职销售：

1. 验证客户为 `recycled(sales_return)`。
2. 设置新的 `owner_id`。
3. 设置 `lifecycle_status='active'`，清空全部回收字段。
4. 设置 `assignment_status='assigned'`，生成新的领取截止时间，清空旧退回原因。
5. 如果有关联入库记录，同步为 `assigned`，更新负责人和领取截止时间，保留 `crm_customer_id`。
6. 写入审计日志。

客户重新出现在新负责人的待领取流程中；销售领取后继续使用原 CRM 客户及其历史记录。

### 手工删除

管理员只能删除符合“手工创建客户识别”条件的活跃客户。

事务内执行：

1. 验证真实管理员身份、专用权限、客户来源和活跃状态。
2. 保存原负责人。
3. 设置 `lifecycle_status='recycled'`、`recycle_kind='manual_delete'`、原因、执行人和时间。
4. 设置 `owner_id=NULL`。
5. 保留客户和全部衍生数据。
6. 写入审计日志。

手工删除客户不进入普通未开发线索池、线索分配中心、CRM 全景、管道或经营统计，只进入回收站“手工删除”页签。

### 恢复手工删除客户

管理员可以恢复 `recycled(manual_delete)` 客户：

- 原负责人仍是在职销售时恢复给原负责人。
- 原负责人不存在、已归档或已停用时，恢复为未分配活跃客户。
- 清空全部回收字段。
- 不修改客户阶段和历史数据。
- 写入审计日志。

## API 设计

新增以下端点：

### `GET /api/sales-crm/accounts/recycle-bin`

仅返回当前账号有权限管理的回收客户，支持：

- `kind=sales_return|manual_delete`
- `search`
- `page`
- `pageSize`

响应包含客户摘要、原负责人、操作人、原因、回收时间和可执行操作，不返回无权查看的联系人字段。

### `POST /api/sales-crm/accounts/:customerId/return`

销售退回自己的客户，或经理退回单个可管理客户。

请求：

```json
{ "reason": "客户暂时不适合继续由当前销售跟进" }
```

### `POST /api/sales-crm/accounts/bulk-return`

经理或管理员批量退回。

请求：

```json
{
  "customerIds": ["CRM-1", "CRM-2"],
  "reason": "重新平衡区域和语言能力"
}
```

### `POST /api/sales-crm/accounts/:customerId/trash`

管理员手工删除客户。

请求：

```json
{ "reason": "误创建的重复手工客户" }
```

### `POST /api/sales-crm/accounts/:customerId/restore`

管理员恢复手工删除客户。请求体为空对象。

### `POST /api/sales-crm/accounts/:customerId/reassign`

经理或管理员重新分配销售退回客户。

请求：

```json
{
  "ownerId": "USR-SALES",
  "reason": "按区域和语言重新分配"
}
```

### 错误协议

- `400 INVALID_RECYCLE_REASON`：原因缺失或长度不合法。
- `400 INVALID_RECYCLE_KIND`：操作类型不支持。
- `403 CUSTOMER_RECYCLE_FORBIDDEN`：无权操作目标客户。
- `403 REAL_ADMIN_REQUIRED`：手工删除或恢复不是由真实管理员执行。
- `404 CUSTOMER_NOT_FOUND`：客户不存在或不可见。
- `409 CUSTOMER_ALREADY_RECYCLED`：客户已经在回收站。
- `409 CUSTOMER_NOT_RECYCLED`：恢复或重新分配的客户不是回收状态。
- `409 RECYCLE_KIND_MISMATCH`：对错误回收类型执行恢复或重新分配。
- `409 MANUAL_CUSTOMER_REQUIRED`：目标不是可手工删除的客户。
- `409 RECYCLE_STATE_CHANGED`：批量验证后状态发生变化。

错误响应不得包含客户联系人、询价或订单详情。

## 权限模型

新增两个权限：

- `manage_customer_recycle`：默认管理员和经理允许；用于查看回收站、经理批量退回和重新分配。
- `manage_manual_customer_deletion`：默认仅管理员允许；同时受真实管理员限制，用于手工删除和恢复。

销售退回自己的客户不要求管理权限，但必须通过现有客户访问范围和 `edit_customer` 权限检查。

所有危险操作在身份模拟期间禁止。服务端权限检查是最终边界，隐藏按钮不能替代 API 校验。

## 查询与统计隔离

所有活跃经营查询必须显式限定：

```sql
COALESCE(a.lifecycle_status, 'active') = 'active'
```

至少覆盖：

- CRM 客户全景和客户详情入口
- 驾驶舱汇总
- 管道与漏斗
- 国家、批次和销售能力报表
- 活跃客户负荷和自动分配算法
- 今日待办与超期预警
- 普通销售的客户访问范围
- AI 客户列表和以 CRM 客户为边界的任务入口

客户回收站使用独立查询，不复用活跃客户列表后在前端过滤。

未开发线索池需要区分：

- `sales_return` 客户只在回收站等待重新分配，不显示为普通可用线索。
- `manual_delete` 客户只在回收站“手工删除”显示。
- 回收客户仍然算作已有 CRM 关联，避免被每日扫描重新导入并创建重复客户。

直接按已知客户 ID 加载详情时也必须执行生命周期和权限检查。回收客户详情只能由回收站管理接口访问，普通客户详情端点返回 404。

## 前端交互

### CRM 客户全景

- 批量负责人下拉框只包含有效销售，不包含“不分配”。
- 增加独立“批量退回”按钮，打开原因确认弹窗。
- 客户抽屉增加“退回客户”；销售只对自己的活跃客户可见。
- 符合手工创建条件且当前用户有权限时显示“删除到回收站”。

### 已领取

- 销售对已领取客户看到“退回”操作。
- 经理看到“重新分配”和“退回到回收站”，不再使用空负责人表达退回。

### 客户回收站

新增导航项“客户回收站”，默认仅管理员和经理显示，包含：

- “待重新分配”：`sales_return`
- “手工删除”：`manual_delete`

列表显示客户、原负责人、操作人、原因、时间和操作：

- `sales_return`：经理或管理员选择业务员后重新分配。
- `manual_delete`：真实管理员恢复。

所有退回和删除操作要求填写原因并二次确认。恢复和重新分配显示将恢复的客户及负责人结果。

## 并发与事务

- 单个和批量操作均使用 SQLite `IMMEDIATE` 事务。
- 权限检查后必须在事务内重新读取目标状态，不能依赖前端或事务外快照。
- 批量操作采用全有或全无语义。
- 重复提交不得覆盖第一次回收的原因、操作者和时间。
- 恢复与重新分配只有一次能从指定回收状态成功迁移到活跃状态；后续请求返回 `409`。
- 数据库失败时回滚账户和入库状态，不能出现一边活跃、一边已退回的状态。

## 审计

复用现有 `crm_audit_log`，记录：

- 路由和动作类型
- 真实用户、有效用户和身份模拟上下文
- 目标客户 ID 或批量目标数量
- 回收类型
- 原负责人和新负责人
- 原因
- 操作结果和时间

日志不记录联系人详情、询价内容、报价金额、订单详情或会话凭据。

## 测试策略

### 后端

- Schema 迁移为现有客户补齐 `active` 默认状态。
- 销售只能退回自己的活跃客户。
- 经理可批量退回可访问客户，任一无权目标导致全量回滚。
- 手工删除只接受真实管理员和可识别的手工客户。
- 回收操作不删除或修改客户主档和全部衍生数据。
- 关联入库记录与 CRM 生命周期保持一致。
- 重新分配恢复原 CRM ID 并生成新的领取时限。
- 手工恢复在原负责人有效和无效两种情况下行为正确。
- 重复退回、重复恢复、错误回收类型和并发状态变化返回正确错误码。
- 回收客户不进入活跃查询、统计、预警、负荷和每日扫描。
- 普通客户详情不能越权读取回收客户。

### 前端

- 批量负责人下拉框不再提供“不分配”。
- 已领取客户显示符合权限的退回操作。
- 手工删除按钮只在正确来源和权限下显示。
- 回收站两个页签、空状态、原因弹窗、恢复和重新分配操作正确。
- 身份模拟期间危险按钮隐藏且 API 仍拒绝请求。

### 回归

- 现有销售 CRM、权限、数据维护、入库分配、AI 客户范围和部署测试全部通过。
- 使用临时 SQLite 数据库验证，不读取或写入生产数据库。
- 部署后只执行只读聚合检查和人工页面验证，不使用真实客户试做删除。

## 发布与迁移

数据库迁移只增加带默认值的字段和必要索引，不重写现有客户状态。部署前执行完整测试和候选数据库迁移验证。

生产发布后检查：

1. 现有客户全部保持 `active`。
2. 客户、活动、联系人、询价、报价、订单和 Recon 数量不减少。
3. 现有未分配客户仍是活跃客户，不自动进入回收站。
4. 新回收站初始为空。
5. 普通 CRM 页面、入库分配和 AI 客户范围无回归。

不通过生产客户执行破坏性烟测；使用发布验证数据库覆盖退回、删除、恢复和重新分配流程。

## 验收标准

1. 销售可以填写原因并退回自己的已领取客户。
2. 经理和管理员可以批量退回客户并重新分配 `sales_return` 客户。
3. 管理员可以把符合条件的手工客户移入回收站并恢复。
4. 回收客户只在回收站显示，不参与正常 CRM、管道、预警、负荷和统计。
5. 所有客户主档和衍生数据在退回、删除、恢复和重新分配前后数量及关联保持不变。
6. 恢复或重新分配继续使用原 CRM 客户 ID。
7. 空负责人不再承担退回语义。
8. 权限、身份模拟、错误类型和批量原子性符合设计。
9. 所有操作可审计且不记录敏感业务详情。
10. 全量自动化测试通过，候选数据库迁移验证通过，生产只读检查无数据减少。
