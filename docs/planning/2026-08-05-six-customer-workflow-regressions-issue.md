# 客户流转与经理协助闭环回归：汇总 6 个生产问题

## 背景

在当前生产基线 `2ca86c800ff3da4e36fb2ba30ba278292116dd20` 上，按销售、主管/经理账号完成真实业务流程后，确认存在 6 组相互关联的问题。它们横跨今日待办、主管介入任务、线索池、客户回收站、客户资料编辑和客户详情抽屉。

本 Issue 用作唯一的统一跟踪和端到端验收入口。

## 问题清单

### 1. 销售发起“需要经理协助”后，经理待办错误显示给销售

**实际行为**

- 销售记录新进展并勾选“需要经理协助”；
- 销售自己的“今日待办”出现 `MANAGER_NEEDED / 需要管理者介入`；
- 该行没有可执行动作，只显示“当前账号无权处理”。

**根因**

后端先按客户可见范围生成全部待办原因，再只清空当前账号无权执行的动作，没有在分组和计数前过滤经理专属原因。因此销售仍收到经理任务，角标、原因数、主要原因和汇总同时错误。

**期望**

`MANAGER_NEEDED` 只进入有权处理的经理/管理员待办。销售可查看“等待经理响应”的只读状态，但不应把经理任务显示为自己的待办。后端越权执行仍必须返回 `403`。

### 2. 经理完成协助后，今日待办清零且没有已处理记录

**实际行为**

- 经理完成协助后，客户状态、活动和审计会更新；
- 今日待办由实时状态计算，完成后该行立即消失；
- `crm_manager_tasks` 和 `crm_manager_interventions` 没有记录；
- “主管介入任务”无法查看这次请求及处理结果。

**根因**

销售主动请求经理协助与主管介入任务是两套独立模型。当前主管任务仅支持 `consecutive_deferred`、`first_contact_silence`、`planned_action_overdue` 三类阈值触发原因，且任务扫描没有前端或仓库定时任务自动调用。

**期望**

将销售主动请求经理协助持久化为稳定任务/请求，建议接入“主管介入任务”的 `open -> completed` 模型。已处理记录至少包含客户、销售申请人、申请时间/原因、处理经理、处理意见、完成时间、活动和审计引用。

### 3. #241 新退回流程已实现，但客户回收站仍默认展示历史销售退回

**核查结果**

- #241 已实现新的写入流程：新销售退回进入线索池，标记不对口进入 `mismatch` 回收站；
- 生产中的 70 条 `sales_return` 均早于 #241 部署，未发现部署后新增；
- 但旧 `sales_return` 数据仍保持 recycled，回收站仍保留并默认打开“销售退回”分类；
- 页面说明仍沿用“退回进入回收站”的旧语义。

**结论**

#241 核心新流程已实现，但历史数据处置和页面展示收口未完成，用户可见验收只能视为部分完成。

**期望**

正常回收站只展示“不对口”和“手动删除”。历史 `sales_return` 需要先生成可核对、可回滚的迁移/归档方案，经业务确认后再处理，不能直接删除或批量改写生产数据。

### 4. 销售退回线索没有勾选框，无法重新分配

**实际行为**

退回线索保留原 `crm_customer_id` 和开发历史。后端明确允许该类 returned 客户复用并重新分配，但前端 `intakeItemAssignable` 同时要求 `in_crm=false` 且 `crm_customer_id` 为空，导致行勾选框、全选和批量分配入口全部消失。

**期望**

销售退回本质上恢复为待分配，只额外显示“曾退回”标签。具备 `manage_intake` 权限的账号可以单条/批量重新分配，并复用原 CRM 客户 ID 和全部开发历史；普通重复客户仍保持不可分配保护。

### 5. 编辑客户资料被“下一步计划”校验阻断

**实际行为**

#246 将下一步动作和计划时间并入“编辑客户资料”统一表单。客户已有过期计划时，即使用户只修改国家、行业或官网：

- 前端仍校验未修改的历史计划时间并拒绝提交；
- 即使绕过前端，PATCH 仍携带 `nextAction/nextActionAt`，后端再次以 `NEXT_ACTION_AT_MUST_BE_FUTURE` 拒绝整个请求。

**期望**

“单一编辑入口”不等于“单一业务事务”。客户资料保存不得携带或校验下一步计划；计划应由明确的跟进/计划入口维护。lost/disqualified 重新激活等确需计划的动作应走显式流程。

### 6. 客户抽屉出现空异常卡，“查看客户历史”像假按钮

**空异常卡根因**

无 `view_contacts` 权限时，通用递归脱敏器会删除提醒对象的 `title`、`detail`、`action`、`summary`、`nextAction` 等字段。前端仍按提醒对象存在渲染卡片，所以只剩红色边框和空胶囊。

**历史按钮现状**

Issue #227 的后端历史接口已经实现并能返回 `200`，按钮并非纯占位。但结果被追加到现有时间线下方，页面不滚动、按钮状态不变；旁边又有真正打开弹窗的“展开完整时间线”，因此用户当前视口看不到反馈并判断为假按钮。

**期望**

- 联系人脱敏必须按数据结构/允许列表处理，不能误删业务提醒字段，同时不能泄露真实联系人信息；
- 核心提醒字段为空时不渲染空卡；
- 合并或清晰区分两个历史入口，点击后 loading、成功、空结果和失败状态必须在当前视口可见。

## 统一修复原则

1. **权限可见性与动作权限分开定义**：不能只清空按钮而保留错误任务、错误计数或空对象。
2. **待办必须有持久闭环**：需要回看的任务不能仅依赖客户当前状态实时投影。
3. **前后端使用同一业务判定**：线索是否可分配、客户是否可恢复等复杂规则应由后端返回明确字段，前端不重复推断。
4. **单一入口不等于字段强耦合**：客户资料、阶段流转、负责人和计划可以统一导航，但必须保持独立校验和提交边界。
5. **历史数据与新流程分开处理**：先保证新写入正确，再通过只读清单、备份和可回滚方案治理旧数据。
6. **交互验收以用户可见结果为准**：不能只检查接口 200 或源码中存在按钮。

## 统一验收标准

- [ ] 销售发起经理协助后，销售今日待办不包含 `MANAGER_NEEDED`，经理可见且可处理。
- [ ] 同一客户存在销售原因和经理原因时，各角色的原因、主要原因、紧急程度、角标和分页统计均按授权范围重新计算。
- [ ] 经理完成后，可在主管介入任务或明确的已处理入口查到完整申请与处理记录。
- [ ] 阈值型主管任务具备明确的自动扫描机制，重复扫描保持幂等。
- [ ] 新销售退回只进入线索池；新不对口只进入 mismatch 回收站。
- [ ] 客户回收站默认不展示历史销售退回，页面说明与 #241 新语义一致。
- [ ] 历史 `sales_return` 先审计、备份并确认迁移/归档方案，不直接删除生产数据。
- [ ] returned 且关联原 CRM 客户的线索可勾选和重新分配，领取后复用原 CRM ID，历史不丢失。
- [ ] 客户存在过期或不完整的历史计划时，编辑基础资料仍可独立保存，资料 PATCH 不携带计划字段。
- [ ] 独立计划入口继续严格拒绝过去时间，不能因解耦而放宽后端计划规则。
- [ ] 无联系人权限账号仍能看到完整业务提醒，但看不到联系人敏感字段；页面不出现空异常卡。
- [ ] 客户历史点击后在 720px、900px 和移动端常见视口中均有立即可见的反馈和结果。
- [ ] #227、#241、#246 已有正确能力保持不回归。
