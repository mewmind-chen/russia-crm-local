## 用户反馈

经理评价存在两种不同的评价对象：

1. **企业评价**：经理对企业本身的经营情况、采购机制、合作价值、风险和开发策略作出判断。
2. **联系人评价**：经理对该企业内具体采购、采购主管、老板或其他对接人作出判断。

一个企业可能有多个不同对接人，因此联系人评价不能只挂在企业名下，也不能只保存一段联系人姓名文本。写联系人评价时必须选择本次评价关联的具体联系人，以便后续准确区分评价对象和查看各联系人的历史评价。

经理评价应出现在完整客户资料页。在当前“概览 / 联系人 / Recon / 标签”页签同级增加“经理评价”页签，页签内再分为“企业评价”和“联系人评价”两部分。

当前 CRM 客户全景的右侧快速抽屉错误地展示了“企业经营评价 / CRM 对接人 / 对接人评价”三块内容。抽屉宽度不足，内容出现压缩、截断和层级混乱；这些模块不应继续出现在右侧抽屉中。

## 当前行为

### 1. 评价入口和联系人资料混在右侧抽屉

客户详情抽屉依次渲染：

- `MANAGER INSIGHT / 企业经营评价`
- `CONTACT PROFILE / CRM 对接人`
- `CONTACT INTELLIGENCE / 对接人评价`

这三块位于客户操作区和完整客户时间线之间。抽屉主要用于快速查看和快速操作，但当前同时承担联系人维护、企业评价和联系人评价，导致内容过长、显示不完整，也让“客户资料”和“经理判断”的信息边界不清楚。

当前代码位置：

- `sales-assets/app.js:8050-8069`：抽屉中的企业评价、CRM 对接人和对接人评价
- `sales-assets/app.css:89`：上述评价卡片与联系人卡片样式

### 2. 完整客户资料页没有经理评价页签

从抽屉点击“查看完整客户资料”后，完整客户资料页当前提供：

- 概览
- 联系人
- Recon
- 标签

“联系人”已经是独立资料页签，但经理评价没有对应页签。因此经理只能返回窄抽屉或从左侧全局“经理评价中心”寻找企业，无法在单个客户的完整上下文中集中查看和新增两类评价。

### 3. 联系人评价的现有数据模型已区分对象，但关联校验不完整

现有评价表和接口已经支持：

- `subject_type = company | contact`
- `subject_id`
- `subject_name`
- `subject_title`

现有抽屉通过点击某个联系人旁边的“评价此人”，把联系人 ID、姓名和职位写入隐藏字段。这个操作依赖联系人卡片作为入口，没有“写评价后选择关联联系人”的独立流程。

### 联系人 ID 的来源

评价关联 ID 应直接使用联系人接口返回的 `contact.id`，经理不需要填写。当前联系人列表由 `GET /api/sales-crm/profile/:customerId` 返回到 `accountContacts`，包含两类对象：

- 人工维护的 CRM 联系人：数据库表 `crm_account_contacts` 生成原始 ID（后端使用 `id('P')`），对外返回 `local:<原始ID>`，例如 `local:P-...`；
- Recon 联系人候选：来自 `person_candidates.person_id`，对外返回 `person:<person_id>`。

页面选择联系人时应同时显示姓名、职位/角色和来源（人工录入 / 联系人研究），提交完整的不透明 ID。后端再根据 ID 前缀和当前客户的联系人列表校验真实归属，不能根据姓名、职位或前端自行拼接的字符串建立关联。

后端创建联系人评价时目前只检查 `subject_name` 非空，没有确认：

- `subject_id` 是否对应真实联系人；
- 该联系人是否属于当前客户；
- 姓名和职位是否与该联系人记录一致。

因此后续迁移入口时不能只增加一个前端下拉框，还需要保证评价和联系人的真实归属关系。

## 期望信息架构

### 完整客户资料页

页签调整为：

```text
概览 | 联系人 | 经理评价 | Recon | 标签
```

其中：

- “联系人”页签继续维护该企业的 CRM 联系人资料；
- “经理评价”页签集中展示和新增企业评价、联系人评价；
- “Recon”与“标签”保持现有职责。

### 经理评价页签

页签内包含两个明确分区：

#### 企业评价

- 评价对象固定为当前企业；
- 展示该企业的历史经理评价，至少包括评价原文、评价人和评价时间；
- 有 `manage_evaluations` 权限时可以新增评价；
- 新增内容保存为 `subject_type = company`。

#### 联系人评价

- 展示当前企业各联系人的历史经理评价；
- 联系人至少显示姓名和职位/角色，例如采购、采购主管、老板；
- 新增评价时，经理先填写评价内容，再选择“关联联系人”；
- 关联联系人为必选项，只能选择当前企业“联系人”页签中 `accountContacts` 返回的真实联系人或联系人候选；
- 保存后写入 `subject_type = contact` 和真实 `subject_id`；
- 一个企业可有多个联系人，每条评价只关联一个联系人，同一联系人允许保留多条历史评价；
- 没有联系人时显示明确空状态，并引导先去“联系人”页签新增联系人或补充联系人研究，不能保存未关联的联系人评价。

## 右侧抽屉调整

右侧客户详情抽屉中移除以下完整模块：

- 企业经营评价
- CRM 对接人
- 对接人评价

抽屉继续保留适合快速浏览和操作的内容，例如：

- 客户阶段和下一步计划；
- 客户关键资料摘要；
- 记录进展、编辑资料、退回或标记不对口等操作；
- 客户时间线及进入完整客户资料的入口。

抽屉不再承担联系人资料维护和经理评价维护。用户需要处理联系人或评价时进入完整客户资料页的对应页签。

## 权限边界

- 有 `view_insights` 权限：可以查看授权客户范围内的经理评价。
- 有 `manage_evaluations` 权限：可以新增企业评价或联系人评价。
- 无 `manage_evaluations` 权限：不显示新增评价操作，但可按 `view_insights` 权限只读查看。
- 联系人候选列表必须同时遵守客户数据范围和联系人可见权限。
- 后端必须校验联系人真实存在且属于当前客户，人工联系人和 Recon 候选分别校验 `local:` / `person:` 前缀；不能信任前端提交的 `subjectName`、`subjectTitle` 或任意 `subjectId`。
- 左侧全局“经理评价中心”可继续作为跨客户检索和覆盖率总览；本问题不要求删除该入口，但单个客户的评价查看与填写应在完整客户资料页形成闭环。
