# 问题 2：经理完成协助后没有可查看的已处理记录

## 记录信息

- 状态：已定位，未修复
- 记录日期：2026-08-05
- 正式仓库：`mewmind-chen/russia-crm-local`

- 调查分支：`codex/fix-sales-manager-assistance-tasks`
- 关联问题：`2026-08-05-manager-assistance-today-task-visibility.md`
- 影响角色：经理、管理员
- 影响页面：今日待办、主管介入任务

## 用户反馈

经理账号在“今日待办”看到“需要管理者介入”，点击处理并填写结果后，今日待办立即清零，页面没有“已处理”记录；“主管介入任务”中也没有对应内容。

业务期望至少满足一种可追溯方式：

1. 今日待办提供“已处理”记录；或
2. 经理协助请求及处理结果进入“主管介入任务”，并可按已完成状态查看。

当前两处都无法查看这次协助的完整闭环。

## 实际行为复现

在最新基线的临时测试数据库中创建一条销售发起的经理协助请求，以经理账号完成后核对：

| 检查项 | 处理前 | 处理后 |
| --- | --- | --- |
| 今日待办包含 `MANAGER_NEEDED` | 是 | 否 |
| 客户 `manager_required` | `1` | `0` |
| 客户 `manager_status` | `待介入` | `已完成` |
| 客户 `manager_id` | 空 | 当前经理 ID |
| `manager_join` 活动记录 | `0` | `1` |
| 协助完成审计记录 | `0` | `1` |
| `crm_manager_tasks` 记录 | `0` | `0` |
| `crm_manager_interventions` 记录 | `0` | `0` |
| 主管介入任务列表总数 | `0` | `0` |

结论：处理结果并非完全丢失，活动和审计中有底层记录；但没有进入任何面向经理的已处理任务列表。

## 根因定位

### 1. 今日待办是实时状态投影，不是持久任务表

`lib/sales_crm.js:2941` 根据客户当前的 `manager_required` 和 `manager_status` 动态生成 `MANAGER_NEEDED`。

经理完成协助时，`lib/sales_crm.js:5896-5963` 执行以下操作：

- 写入一条 `activity_type='manager_join'` 的客户活动；
- 把客户更新为 `manager_required=0`、`manager_status='已完成'`；
- 写入 `today_task_manager_assistance_completed` 审计记录；
- 返回活动 ID 和完成时间。

下一次加载时，`manager_required=0` 不再满足待办生成条件，所以该行立即消失。今日待办没有独立记录 ID、持久状态或历史查询，也没有“已处理”数据源。

### 2. 经理协助流程与主管介入任务是两套独立模型

“需要经理协助”使用：

- `crm_accounts.manager_required`；
- `crm_accounts.manager_status`；
- `crm_activities.manager_required`；
- `crm_audit_log`。

“主管介入任务”使用：

- `crm_manager_tasks`；
- `crm_manager_interventions`；
- 独立的任务状态、原因、证据、接收人、到期时间和完成结果。

`completeManagerAssistanceTodayTask` 没有创建、查找或完成 `crm_manager_tasks`，因此主管介入页面不可能出现这次协助请求或处理历史。

### 3. 主管介入任务只支持三类触发原因

`lib/manager_tasks.js:22-26` 和表约束 `lib/manager_tasks.js:139-168` 只允许：

| 原因代码 | 默认触发条件 | 默认设置 |
| --- | --- | --- |
| `consecutive_deferred` | 同一客户连续记录“暂无计划”达到阈值 | 连续 3 次 |
| `first_contact_silence` | 客户只有一次有效触达，之后持续无新有效动作 | 14 天 |
| `planned_action_overdue` | 最新明确计划超过计划时间和宽限期，期间没有有效动作 | 超期 48 小时 |

判断逻辑位于 `lib/manager_tasks.js:507-570`。终止或不对口客户不会生成任务。

普通销售勾选“需要经理协助”不属于上述三种原因，当前枚举中也没有 `manager_assistance`，所以不会进入 `crm_manager_tasks`。

设置中虽然还有“销售异常”规则，但它用于统计与管理判断，不是 `crm_manager_tasks` 支持的客户级任务原因。

### 4. 达到规则也不会自动出现在主管介入任务

任务创建需要执行以下链路：

1. 调用 `evaluateManagerTriggers` 判断规则；
2. 调用 `upsertManagerTask` 写入 `crm_manager_tasks`；
3. 可选地向设置中的接收人发送通知。

正式应用中这条链路只由 `scanManagerTasks` 调用，入口是 `POST /api/sales-crm/manager-tasks`，代码位于 `lib/sales_crm.js:5405-5420` 和 `lib/sales_crm.js:11306-11310`。

当前前端只调用主管任务的读取、详情、处理和导出接口，没有调用创建扫描接口；仓库脚本也没有定时扫描主管任务。也就是说，在没有外部调用或预置数据时，即使客户已经达到阈值，“主管介入任务”仍可能长期为空。

### 5. 主管介入任务本身支持已完成历史，但本次协助没有接入

`lib/business_page_filters.js:735-776` 的主管任务列表默认查询所有状态，并统计：

- `open`；
- `overdue`；
- `escalated`；
- `completed`。

前端也能显示 `completed` 卡片并以只读方式打开处理历史，相关逻辑位于 `sales-assets/app.js:4051-4091` 和 `sales-assets/app.js:8210-8263`。

因此主管介入任务具备承载已处理记录的基础能力，只是销售主动发起的经理协助没有接入这套模型。

## 影响范围

- 经理处理后无法在待办工作区回看申请人、申请原因、处理意见和完成时间。
- 今日待办角标从有任务直接变为 `0`，用户容易认为记录被删除。
- 主管介入任务页面与“需要经理协助”的业务含义不一致，页面经常为空。
- 客户活动时间线和审计中虽然保留记录，但不是经理日常任务回溯入口，查询成本高。
- 无自动扫描时，主管介入规则配置可能看似有效，实际上不会产生任务。

## 期望行为

### 最低验收要求

经理完成销售发起的协助后，必须存在一个经理可访问的已处理记录，至少包括：

- 稳定的任务或请求 ID；
- 客户 ID 与客户名称；
- 销售申请人；
- 申请时间；
- 申请原因或当次进展；
- 处理经理；
- 处理意见；
- 完成时间；
- 状态 `已完成`；
- 对应客户活动和审计引用。

### 建议产品归属

优先把“销售主动请求经理协助”接入“主管介入任务”作为新的任务原因，并沿用 `open -> completed` 的持久状态与介入历史。“今日待办”继续只展示当前未完成事项；历史通过主管介入任务的状态筛选查看。

如果产品决定保留在今日待办，则必须为今日待办新增持久记录和“已处理”视图，不能仅从当前客户状态反推历史。两套方案至少选择一套，避免同时维护两份不一致的完成记录。

## 后续修复边界

1. 明确 `manager_assistance` 是否成为 `crm_manager_tasks.reason` 的正式原因。
2. 销售发起协助时持久化任务，而不是等经理处理后补历史。
3. 经理处理必须在同一事务中完成任务、写活动、更新客户状态和写审计。
4. 主管介入任务列表必须可筛选 `已完成`，并在页面上明确展示已完成数量或入口。
5. 保留现有角色、客户范围和 `resolve_manager_tasks` 权限边界。
6. 为阈值型主管任务增加明确的自动扫描触发机制，不能依赖未被前端调用的内部接口。
7. 防止同一协助请求重复创建任务或被不同经理重复完成。

## 建议回归场景

1. 销售发起协助后，经理看到一条稳定的未完成请求。
2. 经理处理后，当前今日待办消失，但主管介入任务可按 `已完成` 查到同一任务。
3. 已完成详情包含申请与处理两端的完整信息，并能关联活动和审计。
4. 销售无权读取或完成经理任务，但可在客户时间线看到允许公开的处理结果。
5. 经理只能看到授权客户范围内的任务，管理员保持全局范围。
6. 三类阈值规则达到条件后无需人工调用接口即可创建任务，未达到条件不创建。
7. 重复扫描和重复提交保持幂等，不产生重复任务或重复介入记录。
